# Chaos 多固件 symbol 适配可行性

日期：2026-11-15。性质：当前源码与构建链评估；尚未实现新的固件目标。

## 结论

可行，但应修改构建系统、固件绑定和 ABI 适配层，不需要修改 Rust/Clang 编译器源码。

推荐第一阶段做到：一份业务源码，导入多套独立固件资料，构建时明确选择一个目标，
为每个目标生成完整安装包。symbol 负责定位入口和全局数据；结构偏移、参数差异、
回调协议和资源格式由目标配置及专用适配器处理。

“导入多个 symbol 文件”本身不能让当前完整 Chaos 自动兼容多个固件。
同名函数地址不同可以查表解决；同名函数 ABI 不同不能靠换地址解决。

## 本次检查范围

检查了生产 Rust 源码中的固件依赖、C 模糊/网络/ChaosConnect 入口、fetch/capatch、
构建与 ELF 后处理、Lua 安装/自启动流程、现有 RW6 迁移代码和记录。
没有把 RW6 的实验模块视为完整 Chaos 已支持 RW6 的证据。

对以下目录去除块/行注释后，粗扫 `0x0C/0x1C/0x20/0x2C/0x3C` 等地址区间：

| 范围 | 地址样式常量出现次数 |
|---|---:|
| `supervisor/src/fw_api/fwaddr.rs` | 85 |
| 其他 Rust `fw_api` | 164 |
| Rust 业务与状态文件 | 342 |
| C 模糊适配与 vendor | 278 |
| C 网络、ChaosConnect | 44 |
| C fetch、capatch | 81 |
| 合计 | 994 |

这些数值去重后为 760 个候选地址常量。它们不是“待适配函数数量”：包含全局数据、
类型标识、地址边界、历史代码和条件编译下的其他目标；未按预处理结果筛选。
统计不包含第三方网络库、测试、生成的网页字节数组和二进制资源。
它说明固件依赖远未全部集中到 `fwaddr.rs`。

## 已存在的基础与具体缺口

| 部分 | 当前情况 | 多固件所需工作 |
|---|---|---|
| Rust 固件入口 | `fwaddr.rs` 已有 t043/tp65 和 `fw-p65` feature；许多封装仍直接 transmute 数字 | 从同一目标资料生成地址表，迁入剩余调用点 |
| 注册与模块启动 | `state.rs` 保存注册/VFS/样式地址；`chaos_ctor` 在加载时就调用固件 | 目标必须在构造函数调用固件前确定，不能进入 Chaos UI 后再选择 |
| UI 与页面描述符 | 页描述符按 116B 构造，业务读取大量固定字段；尺寸多为 336×480 | 目标布局、尺寸、样式/事件/标志常量与页面框架适配 |
| 模糊与 launcher | C 适配强制 RH_TARGET_1043，包含全局槽、类地址、对象字段和原生回调匹配 | 对应固件的生命周期与绘制适配；仅替换 P67_NATIVE 的函数地址不够 |
| 字体/系统设置/快应用动画 | 固件样式对象清单、内存字段、方法表和 hook 槽不只在 fw_api 内 | 全局表/字段资料和方法表布局也要按目标生成或适配 |
| PAN 与 ChaosConnect | BT 地址表、事件结构、连接链表、线程 loop、计时器尺寸为 p67 专用 | 目标 BT/IPC/连接结构适配，保持线程及缓冲所有权约束 |
| fetch/capatch | 独立 C 模块，含网络结构偏移、TLS 槽、MPU/FPB 架构约束 | 与 supervisor 使用同一目标标识，独立构建及验证 |
| 构建与打包 | CPU/soft-float、dist 路径、设备目录、预览格式与尺寸固定；C 对象缓存未按固件隔离 | 贯通目标参数、缓存与产物隔离，校验所有子产物属于同一目标 |

现有 RW6 资料已经给出不能只换 symbol 的例子：

- `fwaddr.rs` 记录 `lvx_list_item_update`：043 的包装使用六参，p65 对应入口四参，语义也不同。
- `p65_style` 记录 WIDTH/HEIGHT/X/Y/ALIGN：043 为 `1/4/7/8/9`，p65 为 `1/2/8/9/0xA`。
- `lv_obj_delete` 的事件码：043 代码使用 `0x24`，p65 资料记录 `0x23`。
- p65 的部分入口需使用 SRAM 真身；文件地址或 flash 影子代码不能统一加基址后调用。

因此 `fw-p65` 仍有明确的 compile_error，不能通过移除该错误把目标标成已适配。

## 三种实现方式

### A. 目标资料生成绑定、按固件编译（推荐）

设计入口示例，以下参数目前尚不存在：

```text
python3 tools/build.py --firmware xiaomi-band-10-pro-3.101.043
python3 tools/build.py --firmware <另一个已完成验证的目标>
```

构建程序读取目标资料，生成 Rust 常量/封装选择与 C 头文件。
保留当前按绝对地址调用固件、最终模块零未定义符号的方式，避免同时引入新的加载器需求。
同 ABI 的调用共享业务封装，不同 ABI 的调用经过目标专用适配器。

Rust `build.rs` 目前只跟踪 CHAOS_BUILD_TIME，需增加目标环境和资料文件的依赖跟踪。
Rust target 目录、C 对象、network/build、dist/stage 和资源均须按固件隔离。
`--skip-ko`、`--skip-fetch` 也必须核验目标标识与资料摘要，不能误用另一固件的旧产物。

### B. 导入链接符号、按固件链接

可将外部函数/数据声明链接到绝对符号，例如用 LLD 的 symbol assignment 或 `--defsym`。
[GNU ld 选项文档](https://sourceware.org/binutils/docs/ld/Options.html) 说明了
`--defsym` 与 `--just-symbols`；[LLD 文档](https://lld.llvm.org/ELF/linker_script.html)
说明其支持链接脚本中的 symbol assignment。

本次用本机实际 rust-lld 做了临时实验：同一份 Cortex-M33/soft-float C 目标文件，
包含一个外部函数和一个外部 volatile 全局数据，分别绑定两套示例地址：

| 示例资料 | fw_probe | fw_state |
|---|---|---|
| A | 0x0C123451 | 0x20100000 |
| B | 0x0C234561 | 0x20110000 |

两份均生成 ET_REL/ARM 模块，两个符号均为 SHN_ABS，无未定义符号，重定位类型为
R_ARM_ABS32/R_ARM_PREL31；通过当前 fix_ko_layout 和 verify_chaos_ko。
这些地址仅用于链接测试，不是可调用固件入口。

该实验只证明链接工具和现有静态校验可接受此输出，未验证固件 modlib 对新增
SHN_ABS 导入路径的处理、加载后的调用或真机稳定性。采用该方式前需补实际加载器探针。
同名 symbol 同时来自两套固件也不会自动按设备选择，必须在构建时消除歧义。
ABI、结构偏移和业务适配仍然需要 A 方案中的目标层。

### C. 单一 ko 运行时兼容多个固件

技术上可以设计，但工程量更大：需兼容 CPU/指令集/浮点 ABI，启动前识别目标，
把入口和全局地址改为运行时绑定，把有结构差异的功能分派到对应实现。
`chaos_ctor` 已在 insmod 期间注册驱动，因此识别/绑定必须早于第一次固件调用。
识别过程本身也不能依赖尚未选择的某套固件地址。

可先考虑“安装器选择目标后加载对应 ko”，作为同一分发流程支持多固件的方案；
但不同设备的容器格式和 Lua 安装环境也需核对，不能先保证一个容器通吃所有机型。

## 目标资料应包含什么

建议每个设备/固件独立存放，symbol 可以导入现有 JSON/CSV/nm 格式，但统一规范化：

1. 设备标识、固件完整版本、精确镜像 SHA-256、CPU/指令集/浮点 ABI/字节序。
2. 函数名、入口地址、Thumb callable 地址、原型、调用线程、参数/返回值与所有权约定。
3. 全局槽/类/样式对象地址，区分“数据本体”与“保存指针的槽”。
4. 结构尺寸、字段偏移、字段位宽、事件/样式/标志编号、方法表槽位。
5. hook 原始入口、允许写入的实例槽、预期身份、卸载恢复方式。
6. 屏幕几何、资源路径及图像格式、安装器/自启动方式、子模块加载限制。
7. 每项证据与验证等级，以及完整功能所需资料的覆盖清单。

可以读取现有 Canopus target 的 symbol JSON 中的 name/prototype/callable_address 等资料，
但不能把缺失的私有结构和 hook 布局假定为相同，也不能把记录中的状态提升成真机已验证。

缺少完整功能所必需的符号、布局或适配器时构建应失败，不能默认回退到 .043 地址，
也不能在没有明确说明的情况下省略图片、网络、fetch 等模块以声称适配完成。

## 建议实施顺序

1. 建立目标资料格式与 symbol 导入器，把现有 .043 的依赖完整收敛，行为保持一致。
2. 先迁移基础注册、VFS、计时器、页面和 UI，再处理字体、设置、模糊、动画、BT 与子模块。
3. 将所有构建入口统一到目标参数，并增加跨目标缓存/资源混用检查。
4. 用第二个精确固件验证：同 ABI 只换资料，不同 ABI 使用已核对的专用适配。
5. 按目标分别进行静态校验、ARM/主机回归、最小加载探针和完整真机验收。
6. 分目标安装包稳定后，再评估多目标分发包或单 ko 运行时适配。

本次仅进行源码评估与临时链接实验，没有启用新的生产目标，也没有改动安装包。
