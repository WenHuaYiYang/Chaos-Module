# v1.2.7-A 静置 CPU 与功耗优化报告

> 范围：融合上游 1.27 之后的一轮 CPU / 功耗排查（提交 `4ca9224` … `0374af5`）
> 目标：降低桌面静置时的 CPU 占用与耗电

---

## 一、实测数据

| 阶段 | 静置 CPU |
|---|---|
| 基线（融合上游 1.27 前） | 43–50% |
| 融合上游 1.27 后 | 反而更高 |
| 中间某次尝试 | 95% |
| 本轮修复后 | 20–30% |

一个关键观察：把维护节拍从 400ms 改到 600ms（+50%），CPU 只变化 3%（读数波动范围内）。
说明静置 CPU 的大头**不在维护节拍上**，而是"与节拍无关的固定频率负载"。
这条推理是后续排查的主线。

---

## 二、根因

### 2.1 核心模式：把"功能启用"当成"有活要干"（4 处）

维护节拍由 `tick_busy()` 决定：只要任一模块返回"忙"，整机就停在
`TICK_FAST_MS = 50ms`（20Hz 唤醒）。以下四处把"功能开着"误判为"忙"，
导致节拍永久无法回落到中档：

| 位置 | 误判原因 | 修复 |
|---|---|---|
| `capture_preview::pending()` | 缩略图槽 `status == 0` 在离开截图 App 后残留（无人推进），`FG_PAGE` 仍停在截图页 → 每拍都"忙" | 加 `APP_FG != 0` 门，只有截图 App 真在前台才为它加快节拍 |
| `notification_icon::pending()` | `ACTIVE` 是"功能启用"标志，一旦开过恒真 | 新增 `busy()`（仅重试未清零或仍持有图源时为真），`background_home::pending()` 改用 `busy()` |
| `s541_launcher::pending()` | 控制条在桌面"可见"就要求 50ms 跟随滚动 | 低功耗档下让路（该功能默认关闭） |
| `P67_BLUR_EXTRA_DEMAND()` | 控制中心/启动器**按钮模糊默认开启**，使该宏恒真，模糊引擎永久"有需求" | 两处配置默认改为关闭；低功耗档强制关闭（双保险） |

### 2.2 与节拍无关的固定频率负载

`supervisor/bridge/bridge.c` 的 ChaosConnect 桥线程：

```c
owner_tick() { poll(); owner_start(rx 有待处理 ? 2ms : 20ms); }
poll()       { /* 每 250ms 做一次"屏蔽中断的连接列表扫描" */ }
```

- 空闲 **20ms 轮询（50Hz）**，与维护节拍完全独立
- 每 **250ms** 一次 `attach()`，注释明确写着 *connection-list scan masks interrupts*
- 该负载在融合上游 ChaosConnect 后出现，时间点与 CPU 从 20–30% 升到 47–50% 吻合

### 2.3 周期拉得过长引发的抖动

把节拍拉到 1s、上游 poll 拉到 4s 时出现过 **95% CPU**：

- `notification_icon` 的 `RETRY_TICKS = 20` 拍 → 1s 节拍下变成 **20 秒**，期间忙闲判定反复翻转
- 4 秒一次 poll 让模糊 owner 心跳超时，上游反复 `detach/commit` 重建整屏纹理
- 定时器在 50ms / 1s 之间来回切换，每次切换都重设周期

**结论：降低唤醒频率时，必须检查下游是否有"基于拍数"的超时逻辑。**

## 三、逐项修复

### 3.1 修复静置高 CPU（`4ca9224`）

- `capture_preview::pending()` 增加前台门（见 2.1）
- 关闭控制中心 / 启动器按钮模糊（默认值 + 低功耗档双保险）
- `cc_buttons_poll` 纳入空闲降频

### 3.2 修复节拍抖动（`304fa87`）

- `notification_icon`：新增 `busy()` 并替换 `background_home::pending()` 中的 `pending()`
- `s541_launcher::pending()`：低功耗档下返回 false
- 节拍 **1000 → 600ms**；上游 poll 倍数 **4 → 2**
  - `poll_skip` 注释记录：4 倍间隔会触发 owner 心跳超时，宁可少省不能抖动

### 3.3 关掉不用的常驻功能（`4a6a33e`）

- `cc_buttons_config` / `launcher_buttons_config` 的 `ENABLED` 默认 `true → false`
  （配置项保留，系统美化 → 模糊区域 可手动开启）
- `capture_preview::poll()` 快速路径：九个槽位全空且无 JOB 时直接返回

### 3.4 降低固定频率负载（`0374af5`）

| 项目 | 原值 | 现值 | 低功耗档 |
|---|---|---|---|
| 桥空闲轮询 | 20 ms（50Hz） | **100 ms（10Hz）** | 200 ms |
| 连接列表扫描 | 250 ms | **750 ms** | 1500 ms |
| 有请求待处理 | 2 ms | 2 ms（不变） | 2 ms |
| V2 周期重采间隔 | 800 ms | 800 ms | **×2** |

传输速度不受影响：一有请求立刻回到 2ms。

## 四、新增：一个可选的低功耗档

位置：**设置 → 实验性功能 → 极致省电模式**（默认关闭，设置随重启保留）。

打开后它会做四件事：

1. **维护节拍 400 → 600ms**（每秒唤醒次数降一半；有活时仍是 50ms 快拍）
2. **模糊自愈与上游 poll 的检测间隔拉长**（空闲时每两次 poll 才完整校验一次）
3. **关闭控制中心 / 启动器按钮模糊**（它们是持续的额外合成负载，关掉后按钮变回普通样式）
4. **V2 背景重采间隔 ×2**（V2 每次重采都要整屏重绘 + 抓帧 + 滤波）

代价（页面上也写明了）：模糊自愈、通知变化、后台页刷新的响应从亚秒级变成秒级；
装配、滚动、采集和失败恢复仍走快节拍，功能正确性不受影响。

## 七、已知取舍与未解决

### 取舍

1. 低功耗档下通知图标更新最慢约 7 秒（12 拍 × 600ms）
2. 低功耗档下 s541 控制条跟随滚动变钝（该功能默认关闭）

### 未解决

**47–50% 的静置 CPU 尚未锁定真凶**：本轮桥降频仅在 ChaosConnect 启用时生效。
需要按以下隔离测试定位：

1. 关闭 ChaosConnect → 观察 CPU
2. 关闭系统模糊（系统美化 → 系统模糊 → 系统背景）→ 观察
3. 关闭灵动点 → 观察
4. 关闭 s541 控制条 → 观察

若"关模糊"降幅最大，则瓶颈在**模糊层的每帧绘制回调**（60Hz），下一步需检查
vendor `p67_blur` 的 draw 路径是否存在每帧抓帧/滤波。
