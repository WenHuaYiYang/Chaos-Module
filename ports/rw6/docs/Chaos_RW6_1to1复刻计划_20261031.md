### 8.1 平台阻塞三条的共同根：拿不到 ioctl / syscall 入口

- `rtc0`、`uorb/` 下 29 个话题、`usensor` **全是字符设备**（`crw-rw-rw-`），
  订阅/设时间都得 ioctl；
- 模块按未定义符号调 libc 不行（`symtest` 装载 `insmod failed: 2`）；
- 镜像里没有可复用的 `file_ioctl` 封装：vela 文件 API（open/read/close/unlink）
  是 PSRAM 里的真实函数，附近没有 ioctl 兄弟；按“连续代码段指针”扫出的
  9 张候选表里，`svc` 命中全是数据区假命中。
结论：时间·日期、摇一摇轮换两项要落地，先得自建 svc 并定 syscall 序号（未做）。

### 8.2 找 `date`/`clock_settime`：先前的"零引用"是口径错，代码在 XIP（2026-10-31 晚）

**此前判断"这些串在镜像里零引用、NSH 命令的调用点不在 vela_ap.bin"不成立，真实原因是把
"镜像文件偏移"当成了"运行期地址"。** 更正后的取法：字符串运行期在 PSRAM（0x3C 域），
XIP 代码用 **0x3C 域的地址** 引用它们；拿文件偏移 + 0x0C0C0000 去搜当然一个也不中。

实测（从当前 guest 读 0x3C000000 起 4MB，旧 dump 是 10-25 那版固件、地址已漂，不能再用）：

| 串 | 运行期地址 | 引用点（镜像文件偏移） |
|---|---|---|
| `clock_gettime` | 0x3C195F0C | 0x4F4EE8 / 0x4F52AC |
| `%a, %b %d %H:%M:%S %Y` | 0x3C195F2C | 0x4F52B8 |
| `clock_settime` | 0x3C195F7C | 0x4F5298 |
| `timers/rtc.c` | 0x3C16AB60 | 0x41B414 / 0x41B490 / 0x41B4D4 / 0x41B508 / 0x41B540 / 0x41B5A0 |
| `/dev/rtc%d` | 0x3C16AB70 | 0x41B624 |

推论：`date`/`clock_settime` 那一族代码在 XIP 的 **0x0C5B4Exx..0x0C5B53xx**（= 文件
0x4F4Exx..0x4F53xx）；`timers/rtc.c`（RTC 上层）那一族在 **0x0C4DB4xx..0x0C4DB6xx**。
反编译 0x41B420 得到的是"文件对象引用计数递减 + 调析构 + 释放"（close 路径），说明
0x41B4xx 段是 VFS 通用代码，别把它当 RTC settime。

**方法教训**：镜像与 PSRAM 是两个地址域，字符串引用一律按 0x3C 域搜；
`ghidra_fw.py` 的工程 BASE 是 0，查询用**文件偏移**。另：`fn` 会在给定地址**现场造一个函数**，
别把函数中间的地址丢进去（我这么做了一次，工程里多了一个假函数）。

下一步：在 0x0C5B4Exx~0x0C5B53xx 里认 `date` 命令的设置分支，取出它调 `clock_settime` 的目标地址；
RTC 侧再按 `timers/rtc.c` 那一族的调用点找 lower-half 的 settime。两条都先做静态定位，
再按 p65 的规矩编一个"只调一次"的模块在 guest 里做执行验证。

**参考实现的硬件口径**：RTC 不是内存映射寄存器，是 PMU 的 ISPI 通道
（`_ref_miband_qemu` 的 `pmu_rtc_model` / `rtc_base_seconds` / `miband_ispi_set_pmu_rtc_model()`），
所以"直接写 RTC 寄存器"这条路不成立。

### 8.3 写时钟入口已执行验证通过（2026-10-31 晚）

**结论：`clock_settime = 0x0C4C1FB4|1`、`clock_gettime = 0x0C4C205C|1`，可直接从模块调。**

静态定位（方法同 §8.2，按 0x3C 域查串→回镜像找引用）：
- `clock/clock_settime.c` 运行期 0x3C168E20 → 只被镜像 **0x402058** 引用，那是 **0x0C4C1FB4** 的池；
- `clock/clock_gettime.c` 运行期 0x3C168E38 → 镜像 **0x402104**，是 **0x0C4C205C** 的池。
- `struct timespec` 是 **12 字节**：64 位 `time_t`（sec 在 0/4）、`tv_nsec` 在 +8
  （反汇编里正是 `ldr r2,[r1,#8]` 在校验 nsec）。

执行验证（探针 `work/probe_clock`，判据是**固件自己的 `date -u` 输出**）：

| 变体 | 做了什么 | 结果 |
|---|---|---|
| `noop` | 只写结果通道 | 通过（模块装上、DATA 36B、魔数在首址） |
| `logcall` | 调 0x0C504A55 日志入口 | 通过（阳性对照） |
| `getonly` | `clock_gettime(0,&ts)` | 通过：sec=1793430122 ns=891700000，与当时 `date -u`（2026-10-31 07:02:02）一致 |
| `setonly` | `clock_settime(0,&{1700000000,0})` | 通过：设前 `Sat, Oct 31 07:03:10 2026` → 设后 `Tue, Nov 14 22:13:26 2023`，`ret=0` |

**踩过的坑（很值）**：前两版探针一 insmod 就把整机卡死（NSH 503、串口停在命令回显），
根因是**函数指针没置 Thumb 位**——`transmute(0x0C4C_1FB4)` 是偶数，一调就是 INVSTATE 硬 fault。
置成 `|1` 之后两支都正常返回。这就是项目里那条"函数指针必须 bit0=1"。

**语义与边界**（写进实现前要知道的）：
- `clock_settime` 是**绝对时间**语义（不是加偏移），设完固件自己的 `date`、日志时间戳全部跟着变；
- **持久化已确认（2026-10-31 深夜）**：在**同一个 QEMU 实例内**用 NSH `reboot` 让 NuttX 重启，
  设好的 10-30 09:09:57 在重启后读回 **10-30 09:10:52** —— 日期保住了，
  说明 `clock_settime` 这条链本身就把时间落到 RTC 上，**不需要再补 `g_rtc_lowerhalf` 的 settime**。
  （此前"重启回宿主时间"是重启整个 Studio 实例，模拟 RTC 被重置，证不了任何事。）

**下一步（实现层）**：照 10P 的 `time_set.rs` 滚轮配方做 RW6 的时间/日期两页，
保存时把「年/月/日 时:分」换算成 epoch → `clock_settime(0,&ts)`；改完用导航回归 + 截图验，
并用 `date -u` 做交叉判据。

### 8.5 滚轮这一簇的实测（2026-10-31 深夜，探针 work/probe_clock）

在 0x0C240410 起的函数簇里，用"序言扫描 + 反编译 + 探针上屏"认出来的：

| 用途 | 入口 | 证据 |
|---|---|---|
| create(parent) | 0x0C240411 | 探针拿到对象 |
| set_mode(p, mode) | 0x0C240435 | +0x54C/0x54D 模式字节 1 |
| **set_range(p, min, max, step)** | **0x0C24061D** | 调 (p,0,23,1) 后 +0x540=24、+0x53C=数组指针 |
| **set_options(p, const char**, count)** | **0x0C240741** | 反编译定案：按 count×8 分配、逐条 strlen+1 拷贝、写 +0x540=count；mode==1 时 +0x544=count*5。**第二参必须是字符串指针数组**，传整数会当场把 guest 干挂 |
| **set_value(p, index, total)** | **0x0C2377A9** | 就是内部滚动核心 `FUN_001777A8`；上屏实测 `core(p,12,24)` 后滚轮直接显示 **12**（原生皮肤）。循环模式要按 043 的规矩把 index 加上 `2*total` |
| 滚动/重排包装 | 0x0C240871 | 反编译：mode==1 时 `index += offset*2`，再调核心 |

**上屏结论**：`create(当前屏幕) + set_range(0..23) + set_mode(1)` 直接就是**原生皮肤**的滚轮——
截图 `build/shot_picker_show.png` 顶部显示选中项 "00"，不需要另挂样式对象（和 10P 要挂
0x2010D300 那条不同；RW6 建出来就带皮）。默认只显示 1 行、贴左上角。

**还没认出来的三支**（都要先反编译确认语义，不许再盲调）：
1. `set_visible(p, rows)`——要让轮显示 3 行；
2. 取选中项文字/值——**已定案，不用 getter**：反编译滚动核心 `FUN_001777A8`（0x0C2377A8）看到
   RW6 的字段是 `+0x94 首可见索引`、`+0x98 末可见索引`、`+0xFC 选中项在窗内的偏移(u8)`、
   `+0xC0 模式字节`、`+0xC8(u16) 居中用的窗半宽`；所以 **选中值 = (+0x94) + (+0xFC)**。
   （043 那套 +0xF8 偏移在 RW6 挪到了 +0xFC，拿 043 的 +0xF8 读永远是 0——这就是之前差分找不到的原因。）
3. 事件挂法与滚动反馈（10P 的规矩：回调只登记，动作放拍上）。

**已排除的候选**（别再试）：
- 0x0C240740 不是 set_value，是 set_options（上面那条），拿整数当第二参 = 崩；
- 0x0C240870 拿一个参数调用后返回对象自身，不是取文字入口；
- 直接写 043 那套字段（+0x9C/+0x100、+0x94/+0xF8）不生效——RW6 的取值字段不在那；
  实测 +0x94 像是像素坐标（写 12 后读回 46），显示也不跟着变。

0x180870、以及 0x1801D4（set_range/set_options 都会调的"重排"函数），把"选中索引存在哪"钉死。

### 9.1 回归脚本怎么"点得准"（此前随机点错行/点击不生效的根因）

**根因不在页面，在测试手法**，两条都要治：

1. **滚动量不可猜**。手指甩动的实际位移与拖动距离不是 1:1（实测拖 320px，内容走了 552px，
   约 1.7 倍），惯性还带来秒级的不确定位移。旧写法"滑 200 再点固定 y"必然随机点错行
   （实测把「应用管理」点成了「系统美化」）。
   现在改成：**模块在 navdbg 构建里每拍把每张行卡片的屏幕矩形（`lv_obj_t+0x1C` 起 4 个 i32）
   发布到自己的 DATA 段**，结构 `[魔数 0xC0DE00E7, CUR, ROOT, 页根存活, 行数, 24*(x1,y1,x2,y2)]`；
   宿主机用 lsmod 拿 DATA 段、按魔数定位（`chaos_guest.find_magic`），一次 QMP 读拿到全部行坐标，
   按行号点矩形中心。**别用固定的 0x3C7FF000 scratch 页**：那块内存会被别的东西覆盖，
   实测读到过整页 `0x22222222`，症状是"CUR 突然变成 572662306、所有行消失"。
   快照只在 `navdbg` 构建里存在（不发布到正式包；正式包 TEXT/DATA 体积与加这条之前一致）。
2. **甩动会吞掉第一击**。带惯性的快滑之后立刻点，LVGL 把这次按下当成"停滚动"，不发 CLICKED。
   只加"连续两次快照矩形相同"的停稳判定仍会漏（缓动末段整秒不动，看着像停了）。
   改成**慢拖 + 收尾长按 0.45s 再抬手**（不产生甩动），并给导航步骤加"没跳就补点一次"。
   两条都上之后 19 步稳定全过；只上其中一条仍会随机卡在某一击。
3. 翻页动画没走完时点标题栏返回键会被吞：返回动作也必须是"按了等 CUR 真变，没变就补按"。
   更进一步，导航步骤现在自带**失败自愈**：没到目标页就先退回起点页（最多按三次返回）、
   再重点一次，共三轮。实测有一轮"点设置"第一下没到（CUR 还是 0），第二轮自愈通过；
   连续两轮全绿。
4. 应用被系统切走时页根 `spec_attr` 会被清空：快照里的"页根存活"为 0，脚本直接报
   「应用已切走」。实测空闲约 38s 会被切走，所以回归必须边点边读、不能长时间干等。

判据仍是模块自己的 CUR（页号），不靠截图观感；截图只在 `build/` 留档。

### 10.8 补：RW6 文件系统证据（为什么不能做 10P 表盘安装器）

现场 `mount`：


### 10.9 10P 安装器容器在 RW6 上的实测（推翻 §10.4/§10.7 的粗结论）

1. 把 `dist/chaos-installer-10p-043-v1.bin` 推到 `/data/chaos-installer-10p.bin`；
2. 调 `watchface_config_add_new_watchface(id, 容器路径)`（file 0x9B76D8，
   VA `0x0CA776D8|1`）；
3. 固件**确实**在 `/data/app/watchface/market/` 下建出两个目录：
   - `979820261031/`：`resource.bin`（原容器，287616B）；
   - `979820260926/`：`preview.bin` + `_lua/chaos-installer/{main.lua, chaos_sup.bin,
     chaos_icon.bin, chaos_icon_settings.bin, lxgw.ttf}`，文件大小与 10P 容器记录逐条一致。
4. `watchface_config_set_use_watchface`（file 0x9B8988）返回 0；重启后选中该表盘，
   屏幕为全黑。
5. 关键判据：安装器 Lua 若执行过，第一步就会写 `/data/chaos`；实测重启后
   `/data/chaos` 里只有我们原有的 `beautify.cfg/icons/font`，**没有 `sup.ko`**。

### 11.2 装载链（逐字读出来的，不是猜的）

表盘渲染器 `FUN_009C3A3C`（模块名串 `"wf"`，函数名串 `render_file_create` 的那条
分支在 `FUN_009C4644`）按组件类型分派，**类型 8 = Lua 渲染文件**：

| 类型 | 入口 | 含义 |
|---|---|---|
| 2/3/4/5/6/7 | 0x0CA84E04 / 0x0CA85C90 / 0x0CA87310 / 0x0CA84254 / 0x0CA86D10 / 0x0CA89FE0 | 资源型组件（图/文本/指针等） |
| **8** | **`FUN_009C4644` = 0x0CA84644\|1** | **Lua 脚本组件** |

`render_file_create` 的取路径口径（`FUN_009C4644` 体内）：
`buf = param_2` + `"/"` + `node->+0x10`，再用 `FUN_0067DF70` + `FUN_007FD1D8(buf,"lua")`
判这个 `.lua` 是否存在，存在才建 Lua。也就是说**文件名自己带 `.lua` 后缀，
约定是 `<目录>/<名字>.lua`**（mood 就是 `_lua/mood/mood.lua`），
所以 10P 那个 `_lua/chaos-installer/main.lua` 在 RW6 根本不会被找。

它随后调：

```
iVar1 = miwear_lua_run(*0x3C479C68, path, &{obj, 0x0CA84600|1, 0x0CA845E8|1, param_3})
if (iVar1 == 0) return node;              // 装载失败
FUN_00998AC0(iVar1, 0x0CA845D0|1);        // 给这个 lua 实例挂一个回调
EXT_FUN_1C134688(0x3a, 0x0CA84574|1, 0, node);
```

### 11.3 `miwear_lua_run` 的签名与三条硬门（file 0x99897C，VA `0x0CA5897D|1`）

逐字读 `FUN_0099897C` + 它的 `pmain = FUN_009986CC`（字面量池 0x998A88..0x998AB0）：

```
uint32 miwear_lua_run(uint32 app, const char *path, uint32 args[4])
```

1. `app == 0` 或 `path == 0` → 直接早退（args error）。
2. `args == 0` 或 **`args[0] == 0` → 直接早退**。`args[0]` 是这张表盘的根 LVGL 对象，
   会被存进 ctx+0xA0；`args[1]/args[2]` 是渲染回调，`args[3] != 0` 才注册 activity。
   **本轮第一次探针传的是 `[0,0,0,0]`，所以它一步都没走。**
3. 返回值：`pmain` 成功时压 `true` 并返回 1 ⇒ `miwear_lua_run` 返回 ctx 指针（非 0）；
   装载失败/返回假值都返回 0。所以 **`ret != 0` 就是“脚本被装载并跑过”的判据**。

`pmain` 干的活（这就是 10P 那套的 RW6 版）：

| 步 | 内容 |
|---|---|
| 注册模块 | `luaL_requiref` 挂 `miwear`（名字串 `luaopen_miwear` 在 file 0x37C038）、`lvgl`、`screen`、`navigator`、`vibrator`、`activity`、`dataman`、`topic` |
| SCRIPT_PATH | 把 `path` 复制一份，从尾往前找最后一个 `/`，把它置 0 ⇒ 得到目录，`setglobal("SCRIPT_PATH")` |
| package.path | 拼 `<dir>?.lua` 写回 `package.path`（`?.lua` 串在 file 0x37BF24） |
| 装载 | `luaL_loadfilex(L, 原 path, NULL)`，失败就打 `failed to load: %s` 并返回 0 |
| 执行 | `lua_pcall(L, 0, 0, msgh)`，`msghandler`/`l_message`/`lua_panic` 都在这条链上 |

### 11.4 Lua 标准库是全的，`os.execute` 在

`vela_ap.bin` file `0x1C8098..0x1C80C8` 是 Lua 5.4 `os` 库的函数名表：

### 11.6 表盘目录布局定案（guest 现场 `ls`，不是推断）

| 表盘 | 目录内容 | 结论 |

| `builtin/120917365540` | `preview.bin` + `_lua/mood/{mood.lua, ARGB8888/}` | **Lua 表盘没有 config.json**，靠 `_lua/` 这一层识别 |

⇒ §10.9 里“10P 容器解包后不跑 Lua”的**真正原因是文件名**：

### 11.11 RW6 的表盘容器是另一套格式（10P 那套做不出可渲染的 Lua 表盘）

判据来源：把固件自带的 mood 表盘包从 `fw/p65_100_043/vela_resource.bin`
的 `0x1FF3600` 抠出来（72192 字节），已存成参考样本
**`fw/rw6_watchface_mood.bin`（sha256 前缀 4be0ee7eb09b3453）**，与我们的 10P 式容器逐字段对比：

| 偏移 | mood 包（RW6 原生） | 我们的 10P 式包 |
|---|---|---|
| 0x04 | 版本 `0x00010133` | 版本 `0x00010002` |
| 0x10 | `0x903`（记录表尾） | 10P 的 `rec_end` 口径 |
| 0x20 | `0xCF1`（预览块起点） | 10P 的 `0x20` 是另一个字段 |
| 0x28 | pkgName = `120917365540`（**就是表盘 id 本身**） | pkgName = 12 位包号 |
| 0x68 | `ff ff ff ff` + 一串计数（**没有显示名字段**） | 10P 的 `NAME_OFF = 0x68` 是显示名 |
| 0xA8..0x108 | 12 组 `(uid, off)` 的 **widget 表**（指向 0x208/0x3a8/0x448/…） | 10P 的主题表 |
| 0x110 | 主题名 `样式1` | 同位置含义不同 |
| 0x158.. | 又一组 `(uid, off)` 表，off 落在 0x948/0x998/0x9c8… | — |
| 0x903..0xCF1 | widget 元数据：`Mood/心情`、`Stress/压力`、`Steps/步数`、`Heart rate/心率` 各带 4 个 u32 | **完全没有这一段** |
| 0xA48B 起 | `[18 字节名][_lua/mood/mood.lua 内容 8342B][下一条…]`，名不带 NUL，长度取自记录表 | 10P 的 16 字节定长记录表 |

⇒ **渲染节点是从包体内嵌的这张 widget 表建出来的**，不是扫 `_lua/` 目录得来的。
所以 10P 式容器即使被解包出 `_lua/chaos/chaos.lua`，也没有 type 8 的渲染节点，
选上只会是默认表盘。

实测过并排除的三种摆法（都走 `watchface_config_add_new_watchface` + `set_use_watchface`，
两个入口都返回 0，但三条判据文件一个都不出现，重启后 market 目录连节点一起被清）：

1. 外部 id 与容器内 pkgName 相同（都 `979820261101`）；
2. 外部 id 与 pkgName 不同（外 `979820261102` / 内 `979820261101`，照 §10.9 观察到的
   "手机传市场号、容器带自己号"那个形态）；
3. 主题名分别试过 `样式1` 与 `chaos`。

另外两条顺手拿到的事实，省得下轮再查：
- 容器解析是**按格式走虚表**的：`FUN_009D0A40 → FUN_009D00B0(打开) → FUN_009D0198 →
  FUN_009CB0E4`，最后一发是 `(*(class+0x14))(self)` —— 10P 与 RW6 两套头布局由不同
  的 handler 认领，所以"能解包"不等于"认得 widget 表"。
- 整包只有 72192 字节、单个图元约 1440 字节，**没有哪个文件位能塞下 42KB 的 ko**，
  所以"字节等长替换 mood 包里的图元来偷渡模块"这条路不成立，必须真的会写记录表。
