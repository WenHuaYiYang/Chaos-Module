# Chaos → Redmi Watch 6 (p65) 移植：锚点方法与进度

目标：把 Chaos（`chaos_sup.ko` + Lua 安装器）完整移植到 Redmi Watch 6（p65 / best1502p，
固件 3.100.043）。**没有真机**，只有模拟器与逆向，每个锚点都要自行在模拟里验证。

本文件是端口主线的工作文档。模拟器自身的建模问题记在
`docs/Chaos_RedmiWatch6模拟移植_20261010.md`；这份只管"Chaos 要调固件的哪一支、地址是多少、
怎么证"。

## 判据（不许拿别的当进展）

1. 一条锚点**定案**要三件齐全，缺一律标"候选"：
   - Ghidra 给出 p65 函数入口（`who`/`fn` 能落到函数里）；
   - 参数个数/临界区/关键偏移操作与 043 那支对得上（043 侧以官方符号包原型为准）；
   - 模拟器里挂站点看到**真的被执行**（或我们主动调用后返回值合理）。
2. 端口阶段的里程碑判据：ko 能被固件模块加载器接住 → 注册出一个页 → 页面画出内容
   （`dsi 像素载荷` 或 `lcdc 帧` 第一次非零）。指令条数、跑得多远都不算。

## 试过的方法与各自的失效模式（重要，别再走回头路）

1. **函数序言字节对拷**：不成立。同一段 8/16 字节在 043 自己里唯一命中，在 p65 里 0 命中
   （带阳性对照）。两版 LVGL 不是同一次编译。
2. **按名字找**：不可用。LVGL 核心 API 的名字串在镜像里根本不存在；框架名（`app_install` 等）
   存在，但**引用它们的不是代码而是 flash 里的指针表**。
3. **串键 + flash 别名搜引用**（`0x0C`/`0x2C`/`0x28`）：0 命中，因此曾误判"p65 串池无静态引用"。
   **该结论已撤销**：p65 在 file 0x1C0000..0x3C0000 是倒灌进 PSRAM 的 blob，串指针的形态是
   `VA = file + 0x3C000000 - 0x2FDC4`。按 0x3C 域重搜立刻有命中。
4. **串键按 0x3C 域搜**：能命中，但命中的位置**全是数据槽**（`who` 模式逐个判过，37/37 都不在
   函数里）。例：`app_launcher_add` 的名字指针在 file 0x0072C530，它前后是一排指向串池的指针，
   紧接着 0x0072C53C 才是代码（`push.w`）。⇒ 静态搜到的不是"用这枚串的函数"，而是
   "描述这张表的数据格"。
5. **固定窗口取函数体**：越界就会把邻居函数的串当自己的键 —— 实测 6 支不同锚点全投到
   `0x0C876EDC`（键是 `there no one use mana…`）。判据已改成"至少两枚不同键投到同一 ±0x400
   邻域"+ 撞车整批降级；但根本解法是拿 Ghidra 的真函数边界（`FlQuery.java` 已加 `funcs` 模式）。
6. **运行期表**（可用，已出地址）：固件跑起来后会把绑定表填进 PSRAM，`{名字槽 VA, 函数指针}`
   成组、槽距固定。工具 `scripts/scan_fw_ram_tables.py`，明细 `docs/fw_runtime_tables_p65.csv`。
   防伪：单条配对基本是巧合（实测 `ECDSA` 与 `EC_DH` 指同一地址），只认同组槽距一致且 ≥3 条。
7. **动态问"谁读这一格"**（正在用）：既然 flash 里的命中是数据槽，就用 `--rstop <槽的运行地址>
   <长度> <起拍>` 抓读者 —— 读这张表的代码才是真正用它的人。这一条把"静态找不到函数"的死结
   绕开，而且天然满足"锚点在模拟里验证"。

## 已知会挡最终验收的外部缺口

模拟器里固件到不了 launcher：rcS 要 `losetup /dev/loop0 /system/app.bin` 等 8 个文件，
而手上的 p65 全量 OTA 解包只有 `vela_ap/audio/ota/resource/sensor` 五片，
**没有 /system 那段 yaffs**（固件在模拟里读了 10,611 页镜像外内容）。
不挡锚点定位与 ko 构建，但挡"整页 UI 跑起来"的最终验收。

## 24G 长跑（240 设备秒）与注册链候选的现状

run GD1（新 profile，`--deep 24000000000`）：
`执行 24000000000 条后停机=没停(到上限)，指令地址=0C9519BE`，
`gpu … 投活60 完成应答60`、`mcu_mbox … 门铃99 回包75 投递75`、uart1 停在 3304 字节。
⇒ **修掉 BT 之后固件能连续活到 240 设备秒**，中途没有自环、没有断言站点命中。
但 `dsi 像素载荷=0`、`lcdc 帧=0` 到 240 秒仍然为零 —— 与"没有 /system ⇒ 没有 launcher"一致。

一条**还不能算结论**的阴性：`--rstop 0C7EC530 344`（launcher 描述表）跑到 3G 零命中。
p65 读 flash 常走 0x2C 缓存别名，只盯 0x0C 别名很可能压根看不到 ——
下一枪要同时盯 `0C7EC530` 与 `2C7EC530` 才有资格说"这张表没人读"。

## 注册链的两处解析还分不开（记录清楚，别当已定案）

按"串键 → 自己的文字池 → 池前面那支函数"解析，13 处锚点落到了函数入口，但：

- `app_launcher_add`(043 0x0C513A44) 与 `app_launcher_del`(043 0x0C513B2C) 都算到
  p65 `0x0C7EC53C`。手工看字节就知道正确配对是：
  池 `0x0072C520..0x0072C538`（含 `app_launcher_add`、`add icon: %s`）属于**前一支**
  file 0x0072C450；紧接着 0x0072C53C 是下一支的 `push`，它自己的池在
  `0x0072C5B8..0x0072C5C8`（含 `app_launcher_del`、`app_launcher_del ` 错误串）。
  ⇒ **add = file 0x0072C450 / run 0x0C7EC450，del = file 0x0072C53C / run 0x0C7EC53C**。
  解析器把它们撞到同一支的原因是 `own_site()` 取的是"该串指针在镜像里的第一处出现"，
  不是本锚点那一处 —— **已改成按每枚键自己的池定位**（`scripts/p65_anchor_resolve.py` 的
  `own_site()`）。残余限制要记着：它取该键指针在镜像里的**第一处**引用，同一枚键被两个池
  引用时仍需人工分开（`add`/`del` 这两枚键各自唯一，所以这一对没问题）。
- `picker` 两支撞到 `0x0C240410`、`sys` 两支撞到 `0x0CA65DB8` 同理。

⇒ 定案还差最后一步：拿 Ghidra 把 0x0072C450 与 0x0072C53C 两支反编译出来，
与 043 的 `int app_launcher_add(uint16_t app_id)` / `int app_launcher_del(uint16_t)` 对参数与调用形状。
**这一步已经做完**（下一节那两行表格就是它的产物），这两支不再算"待分开的候选"。

## 核对纪律（这一轮踩出来的，写在最前面）

1. **候选必须逐对反编译看过才算**，不能靠自动形状比对批量放行。实测两处翻车：
   - 043 侧有几处锚点地址其实是**跳转桩**（`func_0x…`/`thunk_EXT_FUN_…`），函数体只有 1 条指令，
     按顺序自动配对会把两侧错配成一对（本轮 9 对里有 4 对是桩）；
   - p65 侧 `FUN_00219878`（`lvx_list_item_update` 的候选）反编译结果是
     `halt_baddata()` + "Bad instruction" —— 说明 `who` 的"前驱函数"落在一支**误建的函数**上。
     ⇒ 解析器要把"反编译含 halt_baddata / 行数为 0"当硬筛除条件，不能当命中。
2. 已过逐对核对、可以写进 `fw_api` 的（本轮只有两对）：

   | Chaos 能力 | 043 | p65 | 核对方式 |
   |---|---|---|---|
   | 往 launcher 加一个应用 | `0x0C513A45` | **`0x0C7EC451`** | 双侧反编译逐行同构（`(*(ctx+0x18)+4)` 取回调、`+8` 取 id、链表里比 `*(u8*)(node+0x80)`） |
   | 从 launcher 删一个应用 | `0x0C513B2D` | **`0x0C7EC53D`** | 双侧逐行同构（四参日志、`*puVar2 == param_1` 命中即释放并摘链） |

   这两条正是 Chaos「注册原生应用」要走的入口 —— 端口第一块地基。
3. 还欠一份外部素材才能走到"页面上屏"：p65 全量 OTA 只有 `ap/audio/ota/resource/sensor` 五片，
   **没有 `/system` 那一段 yaffs**（rcS 要 `losetup` 的 `app.bin` 等 8 个文件都在里面）。
   有机器 dump 或工厂包就能补上，模拟器里随之能跑 launcher，剩下的锚点才有可能逐条挂站点验。

## 这一批踩出来的方法（工具与判据，别再走回头路）

1. **解析器两处口径缺陷（都会把候选指错，已修）**
   - `p65_anchor_resolve.py --sites` 打的站点是**绑定表第 7 列的邻域候选点**，而解析时查的是
     **每枚键自己的池位置** —— 两批地址不是同一批，结果 97 支里 83 支被记成"命中点不在紧邻函数上"。
     **那是工具口径不符，不是真阴性。** 修法是两处共用同一个 `keylist()`（含名字键优先）。
     修后：需要问 `who` 的站点 43 处，落到函数入口的从 14 支变 22 支。
   - 多键投票原先按"距函数入口最近"取胜 —— 距离小不等于"是我的池"。实测 `add` 自己的池距入口
     0xE0，隔壁 `del` 的池距 0x84，于是两行都判给 `del`。改成**首键优先**（锚点自己的名字键排最前）后，
     两行自动分到 `0x0C7EC450` / `0x0C7EC53C`，与上一轮手工逐行定案**完全一致**——
     这同时是该规则的独立复现（手工判读与机器判读两条路各自到达同一结果）。
2. **空输入必须显式跳过。** `own_site('')` 拿 `b'\0'` 去镜像里找，命中第一处填充字节，
   再按那个假下标算"引用点"，把几十行推到同一支毫不相干的函数（`0x0C8764B4`）。
   批处理扫描里"空键/空模式"永远不算有效输入。
3. **`who` 的函数记录有洞，序言回查是必需的。** p65 的 `lvx_zoom_picker_set_mode` 在
   `0x00180410` 与它的池 `0x001805D8` 之间**没有 Ghidra 函数记录**（它只经表/指针被调），
   `who` 只能报"前驱函数 + 距离 456"。真入口 `0x00180434` 是往回找 `push.w {r4-r11,lr}` 找到的，
   再让 `FlQuery` 的 `fns` 现场 disassemble + 建函数 + 反编译。
   序言判据要写对：Thumb T1 PUSH 是 `(h0 & 0xFE00) == 0xB400 && (h0 & 0x0100)`。
   第一版写成 `(h0 & 0xF000) == 0xB000 && (h0 & 0x0100)`，把 `0xB1xx`（窄分支/比较）与 `0xBFxx`（nop/it）
   全当成 push，一次扫出 14 个假序言。
4. **"入口"两侧都要各自定证据。** 043 的 `0x0C513BC0`（Chaos 的 `launcher_refresh_app`）
   **不是**函数入口：Ghidra 把它连同自己的文字池一起并进了前一支 `FUN_00513a9c` 的体内。
   拿 `CONTAIN` 的结果当入口，就会拿一段别处函数的反编译去比对，得出"完全不像"的错判。
5. **证明"改地址表没改动默认目标的产物"，要比分节内容、不是整包哈希。**
   整包/目标文件哈希会随 **manifest 路径**变（crate metadata 哈希进成员名），
   与代码无关。做法：`git show <改前提交>:<文件>` 复制一份单独编译，用 `ar x` 取出 `chaos_sup` 的 `.o`，
   按 `.text.* / .rodata.* / .data.*` 三族把每节内容做哈希后**排序成多重集**比对。
   本轮结果：426 / 379 / 11 节逐条相同 ⇒ 043 产物语义等价。（节名里带 crate 哈希，所以不能按名字对齐。）
6. **迁一支"被 043 发版门钉住字面值"的调用点：值的判据留在调用点，用编译期断言钉住漂移。**
   `verify_time_set_release.py` 的 3.6 那组要求"按文件偏移算出来的 VA 出现在**调用点那个文件**里"，
   地址进了 `fwaddr` 之后这条必然误红（踩过一次：只改 `picker.rs`，门里立刻两条红）。
   本来打算把门改成"值在表里核 + 另起 3.6b 核调用点引了 `fwaddr::<名字>`"，两条反写对照也都实测过
   （表里改一位 ⇒ 值那条红；调用点改名 ⇒ 引用点那条红）。但那份门文件带着另一条在飞的大改（约 190 行），
   提门就会把别人的在飞判据一起提进主干 ⇒ 门不动，改调用点这一侧：

### 探针模块的第二轮：连"只装载"都卡，且找到了自助恢复通道

- **自助恢复**：实例的 qemu 留了 `-qmp tcp:127.0.0.1:<port>`（端口每次启动变，从
  `Get-CimInstance Win32_Process` 的命令行里取）。guest 崩一次会自复位并被应用**挂起**
  （QMP `query-status` 是 `prelaunch`, `running:false`）——`cont` 能把它放回运行态，
  不必再杀进程。但**只靠 QMP `system_reset` 重启不完整**：应用在启动时会做一轮
  boot patch（run 目录里的 `boot-patches-applied.json`），QMP 单独复位后固件停在上电早期
  （只到 `RPTUN_INIT_DECLARE`），要应用自己的启动流程才能回到 NSH。
- **`--features empty`（构造与入口都不调任何固件函数）** 这一版还没跑成——guest 每次崩溃都要
  重开实例。但它已经把范围压到"装载路径"：`min`（只在构造里打一行日志）也一样卡。
- **ELF 逐节对比（probe vs chaos_sup）没有发现"缺一节"这类硬伤**：
  两者都是 `e_type=1(ET_REL) mach=40(EM_ARM) entry=0 flags=0x5000200 phnum=0`；
  probe 只有 `.text/.init_array/.ARM.exidx/.rel.ARM.exidx/.rel.init_array/.symtab/...`，
  chaos_sup 多出 `.rodata/.data/.bss/.fini_array/.rel.text/.rel.rodata/.rel.fini_array`。
  下一枪要验的**不是节表，而是文件完整性**：上传任务状态有时是 `conflict`/`queued`，
  而 NSH 里有 `md5` —— 先把本地与 `/data` 的 md5 对上，再谈装载；文件被截断的话
  ELF 头里的大小必然对不上，装载器跳进越界区就是这次"崩+挂起"的形状。
- 操作台落在 `work/probe_p65/g.py`（status/nsh/tail/put/insmod/cont/reset 七个子命令），
  协议口径全写在文件头的注释里（字段平铺、要带 `X-MiBand-Generation`、上传四步、
  回显走串口日志而不是 GET）。

### 装载器口径定案：`e_entry` 必须指到 `module_main`（这一条直接影响安装器）

活体实验（redmi-watch6 guest，NSH `insmod <file> <name>`）：

| 模块 | e_entry | 装进去以后 |
|---|---|---|
| 各节齐全、**什么都不调用**的 no-op 版 | 0（`rust-lld -r` 的默认） | guest 卡死：串口只留一行命令回显，NSH 与 monitor 全 503 |
| 同一个 no-op 版，只把 **ELF 头的 e_entry 改成 `module_main` 的 st_value（0x19，Thumb 位已置）** | 0x19 | **成功**：`lsmod` 列出 `probe_ent  INIT=0x3d49d889  TEXT=0x3d49d870 88  DATA=0x3d49d800 72`，NSH 继续可用 |
| 带锚点调用的完整探针（同一个 e_entry 补丁） | 0x19 | 仍旧卡死 ⇒ 入口/装载没问题，问题在探针**自己调的东西** |

⇒ **p65 的 modlib 拿 ELF 头的 `e_entry` 当模块入口**（`lsmod` 的 INIT 列就是这个值解析出来的），
`-r` 部分链接产物 e_entry 恒为 0，insmod 一跳就死在 0。补丁脚本 `work/probe_p65/patch_entry.py`
（把 e_entry 设成 `module_main` 的节内偏移）已随工程入库。

**对安装器的直接影响**：`Chaos-Module/supervisor/chaos_sup.ko` 现在也是 `e_entry=0x0`。
043 上它能被装进去（用户真机验证过），说明 043 那条装载路径不是拿 e_entry 当入口，
或者安装器自己给了入口 —— 这是**待核**的一点。RW6 这边只要走 NSH `insmod`，
**打包进容器的 `chaos_sup.bin` 必须先补 e_entry**，否则一装就把手表挂死。

完整探针（`ctor` 里先打一行日志 → 读状态块 → `brightness_set_value(137)` →
`brightness_set_full_power(0)` → `page_goto(0xDEAD0000)`）在入口修好之后**仍然卡死**，
下一步按"一次只加一步"逐段二分：先只打日志（`--features min`），再依次加状态块读取、
亮度、page_goto。日志包装是 `0x0C504A55 (level, fmt, …)`，若它在装载上下文里不可重入，
表现也会是"一行都不打就卡"。

**自助恢复的两条路（都不需要人点）**：
- 管理器级 `POST /api/instances/start {instance, skipBinding}`，token 取管理器自己的
  `/config.json` 里的 `controlToken`（实例级 token 不行）；启动后约 9 秒实例的 `config.json` 才可用。

### `open`/`close` 的候选是否证（弱键误配）

043 的 `open`（file 0x00110A28）是标准 NuttX 四参 open：栈上拼 `open_file`、先 `nx_open` 一类、
成功后再挂 file 结构。解析器给的 p65 候选 `FUN_00069980` 是**单参**、分配 0x2c 字节、
调 `FUN_0006b274(3,obj,0,DAT,param_1,0,0,0)` 并置 `+0x14=1` —— 那是驱动/文件对象分配器，不是 open。
`close` 同理（同一批四字母弱键）。

**找法**：先定位 p65 的 `nx_open`/`file_close` 内核实现（形状：取 inode、锁、填 file 结构），
再找它们的公开包装（`open` 四参、`close` 单参，参数一路透传）——
这两支对 Chaos 的 fs 层重要，但不该继续靠 `"open"`/`"close"` 这种串键。

|---|---|---|
| `lvx_zoom_picker_create(0)` | 结果通道返回 **0x3C700618**；对象 `+0x530` 起全 0（无选项）、模式字节 `+0x54D=1` | SIM_CONFIRMED |

### 撤销一条假设：`page_goto` 崩的原因是**调用上下文**，不是实参

三次都崩：无效键 `0xDEAD0000`、合法键 `0x01050000` + 全 0 实参、**当前页自己的键 1** + 全 0 实参。
"实参不能全 0"这条解释被否 —— 共同因素是**调用上下文**：这个函数会动 LVGL 页对象、

（同一批里 `zoom_picker_create` / `vg_font_create_named` 从 NSH 线程调是安全的 ——
它们只建对象、不进动画/主循环。）

⇒ 执行验证要按"上下文"分类：

| 类别 | 例子 | 能否从 NSH 线程的探针验 |
|---|---|---|
| 纯状态写 | 亮度三支、launcher 加/删/刷新、字体建脸 | 能（已验） |
| 建对象但不动主循环 | `zoom_picker_create` / `set_mode` | 能（已验） |
| 主循环/动画/页面栈 | `page_goto`、带真标题的 `page_title_create` | **不能**，要 UI 上下文通道 |

**下一步（UI 上下文通道）**：探针注册一个 `lv_timer`（或把自己挂到某个页的回调上），

### 一条比串键可靠的地址来源：固件自己填的 **vtable**

注册表对象的取法（活体两跳）：
`xd 0x0C7EC868 4` → 注册表对象；`xd <对象> 0x28` → `+0x18` 是 vtable 指针（本轮 `0x3C350B30`）。
vtable 里 12 项**全是 `0x1C15xxxx`（PSRAM 运行别名）**，静态身按

| 槽 | 静态身 | 语义（反编译） |
|---|---|---|
| 0 | 0x180F5C | foreach（收一个函数指针，逐节点回调） |
| 1 | 0x180ECC | **`app_lookup(u16 id)`**：环链按 `*(u16*)(node+0x10)` 查，命中返节点、否则 0 |
| 8 | 0x181848 | 分块遍历（按 `param_2 / 单块大小` 取前 N 个） |
| 2/3/4/5/6/7/9/10/11 | 0x180F04 / 0x181420 / 0x1813F4 / 0x180F7C / 0x180F90 / 0x180FD4 / 0x180FA4 / 0x181024 / 0x181038 | 小 getter 辅助 |

⇒ `app_lookup` 的 p65 地址定案（表项来自运行期 + 语义静态核对）：**run 0x0C240ECD**。
**`app_install` 不在这张表里** —— 它是模块级 API，不在管理器 vtable 上；
下一步按 043 的形状（分配 0x40、清零、把描述符整块 0x40 抄进去、按 `u16[+0x10]` 查重、
挂链、持久化 `/data/apps.json`）在 file 0x180xxx 段里找。

### `app_lookup` 执行确认 + 一条能力：模块能直接调运行期 PSRAM 地址

探针调注册表 vtable 槽 1 的**运行期**指针 `0x1C151109`（PSRAM 低别名），传 19：
结果通道返回节点 `0x3C71C1B0`，读该节点 `+0x10` = `0x13`(19) ⇒ 查询语义坐实（SIM_CONFIRMED）。

两条附带结论：
1. **模块可以直接调 `0x1C15xxxx` 这类运行期 PSRAM 地址**，不必换算成静态 file/run ——
   固件里大批 API（app 管理器、页面管理器）都是经 vtable/PSRAM 分发的，这条能力是安装/注册链的前提。
2. 注册表节点布局**不同于**桌面记录：id 在 `+0x10`（桌面记录在 `+0x00`）、
   `+0x00/+0x04/+0x08` 是指针、`+0x0C` 疑似图标路径。两套结构别混用。

### `app_install` 找到了（静态定案），执行验证卡在"页数组语义"

**地址**：注册表对象 `+0x20` 的函数指针 —— 运行期 `0x1C151AE5` → 静态 file `0x001818A8` / run `0x0C2418A8`。

对 `desc[2]/[3]/[5]/[6]` 四个串字段 strdup → 挂进环链 → 分配 `(count+2)*4` 的页数组并填。

**执行验证失败**：模块自造一个 0x40 描述符（只填 `[2]`=名字串、`[4]`=id 0x7777），
`pages=NULL, count=0` 调进去，**guest 崩**。⇒ 页数组与描述符的字段语义还没掌握，
不能靠"猜一个最小描述符"过。

**下一步（安全路径：克隆现存记录）**：`app_lookup(19)` 拿到节点，
把它的 0x40 字节和 `node[0xC]` 指向的页数组整段 dump 出来 →
在模块里拷一份、只改 `[4]`(id) 与名字串 → 再调 install。这样所有串指针都仍然有效，
唯一的未知量就只剩"页数组能不能共用"。

### 应用描述符 0x40 字节布局（活体读出）与 install 的两次否证

`app_lookup(19)` 的记录（本轮 `0x3C75AF20`）逐格读出：

| 偏移 | 内容 |
|---|---|
| +0x00 / +0x04 | 指针（链表用 + 对象） |
| +0x08 | **包名**串 `com.xiaomi.miwear.activities` |
| +0x0C | **图标路径** `/resource/app/launcher/vitality_...` |
| +0x10 | **u16 app_id** = 19 |
| +0x14 | **版本串** `3.100.043` |
| +0x18 | **构建时间串** `2026.10.01 20:00:18` |
| +0x1C / +0x20 | 两个代码指针 `0x0C737321` / `0x0C737331` |
| +0x30 | **页数组指针**；数组布局 `[count, p0, p1, …]`（本例 count=2） |
| +0x34 | 指针 |

`app_install` 的执行验证**两次都崩**：
① 自造最小描述符（只填 `+0x08` 名字、`+0x10` id）+ `pages=NULL, count=0`；
② 运行期克隆整条 0x40 记录、只改 id/名字、页数组取 `node+0x30` 并传 `(数组+1, count=2)`。
⇒ install 对**页描述符本身**（`p0/p1` 指向的结构）有依赖，光有一条应用记录不够。
下一步：dump `p0` 指向的页描述符，再照造/克隆；或者改走"不新增应用、只改在册应用"的路径
（记录 `+0x0C` 的图标路径本来就是 Chaos 换图标那条链在用的）。

### `app_install` 三次崩溃的真因：**主循环上下文**（不是描述符）

三种调用都崩：自造最小描述符、运行期克隆记录（count=2）、克隆记录（count=0）。
拿崩现场的办法（本轮新打通的通道）：**Studio 的 `/api/debug` 只放行 `info *`，但实例 qemu 的 QMP 端口
直接接受 `human-monitor-command`** —— `info registers`、`xp/<n>xb <phys>`（按字节读内存）、`info mtree` 都能用。

现场读数：`PC=0x0C4F74E8`（**断言哨兵**）、`R0=0x3C1AB6CC`、`R1=212`、`R2=0`、`R3=9`；
`xp/96xb 0x3C1AB680` 解出的串是：
`_path = strdup(app_path)`、`app_verify_info->pkg_path = strdup(pkg_path)`、`libuv/src/unix/async`
⇒ **install 会经 libuv 的 async 句柄向主循环投递**，必须在主循环上下文里调（与 `page_goto` 同类）。
所以前两次"描述符/页数组"的假设都不成立，**崩点与参数无关**。

⇒ 列表里仍差最后一支的 `page_goto` 与 `app_install`，本质是同一个缺口：**主循环上下文通道**。
做它需要：模块注册一个会在主循环里被回调的东西（`lv_timer` 或 async 句柄），
在回调里调这两个 API。找 `lv_timer_create` 的地址仍是下一步的抓手（p65 里没有这个串，
但 `lv_timer_handler` 有 —— 可以顺着它的定时器链表反推结构，或者用 `uv_async_init` 那条已经暴露的线索）。

### 主循环的入口已经露头：uv loop 迭代函数 `FUN_006812ec`

`lv_timer_handler` 这个名字串（池里 file 0x23D1CC）只有一处引用：file 0x6814D0（某函数的字面量池），
前驱函数 = **FUN_006812ec（run 0x0C7412EC）**。它的形状：一个重入闸（上下文 `+0x98`）+
按计数退避 + **遍历一个表**（`DAT_006814C8` 的头/尾，`FUN_0067e1c4/0x0067e1e4` 取头/下一个）+
对每个节点调 `FUN_006c2900(节点[1])`。这看起来就是 **uv loop 的一趟迭代**（回调表），
`lv_timer_handler` 只是这张表里某一项的"名字"。

⇒ 要做"主循环上下文通道"，路线是：找到 libuv 的 `uv_async_init/uv_async_send`
（镜像里有 `libuv/src/unix/async` 这条断言文件串可做键），用 loop 指针挂一个自己的 async 句柄，
回调里再调 `page_goto` / `app_install`。这一条通了，《page_goto + app_install》两支架就一起转正。

### 一个必须先解决的设计问题：**原型也会漂移**（`lvx_list_item_update` 6 参 → 4 参）

p65 的这支（file 0x00159878 / run 0x0C219878）是**四参**、体长 0x38（043 真身六参、0x190）：

```
if (*(int*)(obj+0x54) == 0) { log(3, …); return; }        // 标签对象不在 → 早退
if (param_2 != 0) FUN_001700d8(obj);                      // 设置图标
n = 取 obj+0x44 子对象的主标签文本长度; if (n < 2) return;
FUN_0017fda8(obj, 1);                                     // 四项样式写回 + relayout
```

`FUN_0017fda8(obj, flag)` = 读 `FUN_00198764(obj,0,0x10/0x12/0x12/0x12)` 四次，分别经
`0x00196454 / 0x001983b4 / 0x0019758c / 0x00196764` 写回 `obj+0x44` 那个子对象并 relayout。

⇒ **只做"地址表"不够**：这一支的**原型**在 p65 上不同，Chaos 侧必须按目标给不同的包装
（043 六参 / p65 四参）。地址表的结构要升级成"地址 + 原型/语义"两条，否则编得过、一调就烂。
`rows_sync` 那条链在 p65 上要按上面这套四个 setter 重写，不能照 043 的 `lvx_list_item_update` 直接调。

### 断言的真身：`app_verify_info->pkg_path = strdup(pkg_path)`（第 212 行）

同页有两组串，容易认错：
- `libuv/src/unix/async.c` 属于 `FUN_00561af8`（run 0x0C775AF8）= **`uv__async_io`**：
  从 `*(handle+0x24)` 批读异步 fd（1KB），errno 非 EAGAIN/EINTR/EBADF 时断言（async.c:158），
  然后从 `loop+0x138` 的环链里摘节点回调 —— **这才是主循环处理 async 投递的地方**；
- 而我们崩现场的 `R0=0x3C1AB6CC` 换算成 file 0x1DB490 是 **`app_verify_info->pkg_path = strdup(pkg_path)`**，
  行号 212 ⇒ 崩在**应用包校验**那一步。

**推论（可执行）**：`install` 会调用描述符里自带的两个应用回调（记录 `+0x1C/+0x20`；
app 19 = `0x0C737321/0x0C737331`）做包校验。我们克隆的是**别人的**描述符 ⇒ 它校验的是别人的包 ⇒ 断言。
⇒ 下一次执行验证：把 `DESC[7]/[8]` 换成**模块自己的**两个回调（先给空实现），其余字段仍克隆。
若那时不再断言，就说明"注册一个自有应用"这条路通了。

### install 的进度：换掉描述符回调后，断言从 212 行推进到 147 行（哈希表）

把 `DESC[7]/[8]` 换成模块自己的空回调后，install **走得更深**：
断言从 `app_verify_info->pkg_path = strdup(pkg_path)`（212 行）变成
`util/hashmap.c` 的 **`create hashmap error`（147 行）**。
现场：`PC=0x0C4F74E8`、`R0=0x3C340A90`（该处一带是 `miwear_event` / `system_event` /
`util/hashmap.c` / `miwear_model` 的串区）、`LR=0x0CA3BB81`（调用者在 file 0x97BB80 一带）。

两条结论：
1. **描述符里的两个应用回调确实会被 install 调用**（换掉就改变行为）；克隆别人的描述符必然跑到别人的校验。
2. 下一道闸是"建哈希表失败"——要么分配失败，要么 app 模型管理器没初始化。顺着 `LR=0x0CA3BB81`
   反编译调用者就能分辨。

**顺手记一条操作口径**：Studio 的文件接口与 NSH **互斥**，交替调用会回 `fs-busy`
（"设备或调试连接正被其他操作使用"）—— 上传完要停几秒再发 NSH 命令。

### `app_install` 的执行验证被"app 模型未初始化"挡住（与本机 /system 缺口同类）

第二次断言的 `LR=0x0CA3BB81` 落在 **`FUN_0097BAB8`**：反编译是**哈希表查找/插入**
（`map==NULL` 就在第 146 行断言；键哈希 `h*0x21 + c` 逐字符算；按 `(*map−1) & hash` 取桶逐链比）。
旁边一串 `miwear_model` ⇒ 这张表是 **app 模型管理器**的。

⇒ `app_install` 的前置条件是 **app 模型管理器已初始化**。本台 guest 只跑到 setup wizard，
app 模型没起来 —— 这条执行验证被和"缺 `/system`"同一类的环境缺口挡住。

两个出路（记下来，别乱试）：
1. 找到 app 模型的初始化入口，先调它再装（要读 miwear_model 那支的 init）；
2. 或者在能跑到 launcher 的环境里验（本机没有 `/system`，Studio 的官方包也没有）。

## 镜像的两套运行视图与 LVGL 名字池（2026-10-24，本轮新定案）

### 1) AP 镜像同时被映射到两个地址域（QMP 实测）

| 视图 | 换算 | 实测 |
|---|---|---|
| XIP（flash cache） | `run = file + 0x0C0C0000` | guest `0x0C8BBD18` 读出的字节 == file `0x7FBD18` |
| PSRAM | `VA = file + 0x3BFD023C`（即 `0x3C000000 == file 0x2FDC4`） | guest `0x3C0309C4` == file `0x60788`；`0x3C000000` == file `0x2FDC4` |

- 两套视图**指向同一份字节**：同一支函数从 XIP 地址调、从 PSRAM 地址调都执行同一段代码（已经用亮度三支验证过，调的是 XIP 地址）。
- 但 **PSRAM 只覆盖一段**：`0x3C7FBD18`（= file 0x7FBD18 的 PSRAM 视图）读出全 0，说明 file 0x7FBD18 只在 flash 里、没被拷进 PSRAM。
- 实测 PSRAM `0x3C000000..0x3C200000` 这 2MB 与 file `0x2FDC4..0x22FDC4` 逐 4KB 全部吻合 ⇒ **LVGL 9 的主体就在这一段**（它的日志名字串池在 file 0x20E4xx、类表在 file 0x20E38C 附近，都落在这段里）。
- 结论：静态反编译 **一律用 file offset**；运行地址按视图二选一（本项目的 fwaddr 现在统一写 XIP 视图 `file|1 + 0x0C0C0000`，PSRAM 视图按需现算）。
- 工具：`work/probe_p65/qmpmem.py <地址> <字节数>`（QMP `xp/nxb`，读物理地址，两个别名都能读）。

### 2) LVGL 9 的 `__func__` 日志串 = 名字到函数的桥

镜像里 `lv_*` 名字串 188 个、`lvx_*` 135 个（`scripts/p65_nameref.py` 提取）。凡是函数体里打了 `LV_LOG_*` 的，
它体内就有一个字面量指向**它自己的名字串**（PSRAM 视图的 VA）。于是：

```
file(名字串) --+0x3BFD023C--> PSRAM VA --在镜像里搜 4 字节字面量--> file(字面量) --Ghidra who--> 所在函数
```

- 落盘：`docs/p65_nameref.csv`（434 行，330 处有函数）；工具有缓存，重跑约 40 秒。
- **注意**：CSV 给的是"字面量所在的函数"，被内联的副本也会命中（例如 `lv_obj_get_index` 有 5 个入口）。
  所以它是**候选**，不是定义；用它挑候选再用反编译确认。
- 已经靠这条路把 `lv_timer_handler`（file 0x6812EC）确认下来：定时器结构 = `{+0x00 period, +0x04 last_run,

  实际代码是 `ldr r8,[0x006814c8]` 取指针变量 → 要按"指针变量的地址"找，见下）。

### 3) `lv_obj_create` 一族：p65 首个"能建对象"的确定锚点

从 `lv_obj_class_create_obj`（名字串命中，file 0x115D4）出发，**全镜像只有 1 处直接调用**（file 0x21B90）：

```
0x21B90:  r3=r0(parent); r4=r1
          r1=r3; r0=[0x21BAC] (=0x3C1DE5C8, 即 &lv_obj_class)
          bl 0x115D4          ; lv_obj_class_create_obj(class, parent)
          r1=r4; r4=r0
          bl 0x116C8          ; lv_obj_class_init_obj(obj, ...)
          return r4
```

⇒ **file 0x21B90 = `lv_obj_create`**，**file 0x116C8 = `lv_obj_class_init_obj`**，
**&lv_obj_class = 0x3C1DE5C8**（活体读：`+0x00 base_class=0`（根类）、`+0x04 constructor=0x00386EB1`、
`+0x08 destructor=0x00386E4D`、`+0x0C event_cb=0x00387339`）。

**推论（对移植很重要）**：任意控件的创建 = `create_obj(&该控件的类, parent)` + `init_obj(obj)`。
不必逐个找 `lv_label_create` 这类一行包壳 —— 只要拿到目标类的地址。
其余控件的 create 之所以"没有调用者"，是因为它们把 `create_obj` 内联了。

### 5) 主循环通道的根因改写：不是"线程上下文"，是 **NuttX 任务组的 fd 表**

上一轮把 `app_install` 崩因记成"要在主循环上下文"。本轮把崩现场读全：`R0` 指向
`libuv/src/unix/async.c`、`R1=212`、`R3=9`。212 正是 `uv_async_send`（file 0x561CA0）里
**写 async 管道失败**那条断言，9 = `EBADF`。

⇒ **新假设（待验证）**：NuttX 的 fd 表按**任务组**隔离，insmod 跑在 NSH 的任务组里，
拿不到主循环任务组的 pipe fd ⇒ 写就 EBADF。若成立，`uv_async_send` 从我们的线程**永远**发不出去，
"挂一个 async 句柄再 send"这条线不成立；正确通道是**让固件自己在 UI 线程里回调我们**：
把 `lv_timer` 节点塞进 0x6814C8 那个定时器链表（`lv_timer_create`），回调里再调 `page_goto` / `app_install`。

| 探针 | 只做的事 | 结果 |

  （字面量在 file 0x117D0），第一版按单参调等于把随机 `r1` 当 ctx。这一条先记下，
  等对象创建通了再验证。

⇒ 下一步（不做完不推进）：`mkonly` 再分两档 —— ①只读类结构（不调 create_obj）；
②给一个**活体父对象**（从活页/已建控件读 `+0x24`/`+0x30` 那类格子）再调 create_obj。

**本轮结论（写死在表里，别重复试）**：`mkonly`/`mkpar` 都崩 ⇒ 只靠"探针里调 LVGL 结构函数"这条路
四档全否。下一步只剩两条互斥分支：① `create_obj` 之前的**读**也不安全（先做只读档）；
② 必须先进主循环上下文（`lv_timer` 回调）才允许任何 LVGL 结构操作。

### 8) 建对象打通了：真身地址在 SRAM，走"跳转壳"和 parent=NULL 都不行（SIM_CONFIRMED）

`diag3` 一枪全通（标记页 `0x3C7FF010` 走到 4、结果通道三格齐全）：

| 探针 | 读数 |
|---|---|
| `pick(0)` | 父对象 `0x3D32D6B8` |
| `create_obj(&lv_obj_class, 父)` | 新对象 **`0x3C6451B0`** |
| 新对象 `[+0x00]` | **`0x3C1DE5C8`**（= &lv_obj_class）✔ |
| `obj_ctor(obj, 0)` | 返回，guest 不崩、`ap>` 提示符回来 |

**可用配方（p65 建任意控件）**

```
父 = <活体对象>；类 = <目标类的 PSRAM 地址>
obj = ((void*(*)(const void*,void*))0x003775BD)(类, 父);   // create_obj 真身（SRAM/RAMX）
       ((void (*)(void*,uint32_t))   0x003776B1)(obj, 0);  // ctor/init 真身
```

- `0x003775BD` 的 SRAM 影子源 = **file 0x115D4**（在 0x201775BC 落 64 字节，在 vela_ap.bin 里唯一命中 file 0x115D4）；
  跳转壳在 file 0x19658C（`5f f8 00 f0` + 字面量 `0x003775BD`）。
- `0x003776B1` = 跳转壳 file 0x198B04 的字面量；影子源 file 0x116C8（`lv_obj_class_init_obj`）。
- **两条否证（都试过，别再走）**：
  1. **走跳转壳**（`0x0C25858D` / `0x0C258B05`，即 file 0x19658C/0x198B04 的 XIP 视图）建对象 → 崩；
     `create_obj` 返回 `0x5D` 这种非指针值（拿它当类表/尺寸算是错的），随后 ctor 拿它解引用必崩。
  2. **parent = NULL**（屏幕路径）→ 崩。`lv_obj_create` 那一支（file 0x21B90）本来就是 screen 路径，所以五档全崩与此一致。
- ⇒ 口径：**建控件必须给真父对象，且调 SRAM 真身**。父对象可以从 `lvx_zoom_picker_create(0)` 或活页里拿。

### 9) 崩溃定位的通用手法：标记页

PSRAM `0x3C79A000..0x3C800000` 实测全零，可当 scratch。探针每步前写一个步号到 `0x3C7FF000`
（第二组用 `+0x10`），**复位后宿主机直接 QMP 读**就知道崩在哪一步 —— 不必抢抓现场。
本轮靠它把"建对象"从"整支崩"定位到"ctor 那一步"，省掉十几轮二分。

### 10) 控件类表：`+0x14` 是类自己的日志标签，按它就能认出每个类

每个 `lv_obj_class_t` 的头 9 个字布局（活体 + 镜像双侧一致）：

```
+0x00 base_class   +0x04 ctor      +0x08 dtor        +0x0C event_cb
+0x10 user_data_ctor  +0x14 日志标签串指针  +0x18 instance_size  +0x1C 标志  +0x20 尺寸/标志
```

`+0x14` 指向的串以类名开头（`obj.` / `bar.` / `switch..` / `zoompicker..`），
所以**按标签串就能在类表里认类**。本轮扫 8MB PSRAM（判据：+0x04/+0x08/+0x0C 都是代码指针、
+0x14 是 PSRAM 指针、+0x18 ≤ 0x4000）得到这些类：

`obj / bar / btnmatrix / dropdown / dropdown-list / indicator / lvxlistitem / radio / scale /
slider / switch / textarea / picker / xlist / xcanvas / xtileview / xwin / zoombtn / arcx /
eventinterceptor / pageview / mem / stack / lua`

**label 类不在 PSRAM 段里，在 flash**：`file 0x254608`（XIP 0x0C314608），
`base=&lv_obj_class`、ctor `0x0C78CDC5`、标签串 "label"。**建 label 已执行确认**：
`create_obj(0x0C314608, 父)` + `init(obj,0)` 返回 `0x3C6ABDA0`，且 `[+0x00] == 0x0C314608`。

⇒ 任意控件的类地址都可以这样找：先在 PSRAM 类表里按标签认，找不到就在镜像里搜
`base_class == &lv_obj_class` 的 9 字结构（本轮 label 就是这么定位的）。

### 14) 更正两条此前的结论 + 几何验证卡在哪

**更正 1：`parent=NULL` 不是崩因。** 早先"给 NULL 父对象会走建屏幕路径并崩"是错的 —— 那一批崩溃真正的原因是
**走 flash 跳转壳**（`0x0C25858D`）调 `create_obj`，它返回的是小整数而不是对象指针。用 SRAM 真身
`0x003775BD` 时 `parent=NULL` 正常建出屏幕对象（page2 探针：屏幕 `0x3C6AF250`，其下容器 `0x3C735340`、
`容器[+0x04]==屏幕`）。

**更正 2：`lv_obj_set_local_style_prop` 的入口就是 `0x0C258A5C`**（跳转壳，真身仍是 `0x00378965`）。
按"`movs r1,#imm` + `bl 0x0C258A5C`"扫出 157 个调用点，属性号集中在 **9 / 7 / 8 / 1 / 2 / 5**，
与第 13 节那张表（ALIGN/X/Y/WIDTH/MIN_WIDTH/MIN_HEIGHT）完全吻合 —— 这就是样式漏斗本身，不是别的设置器。

**几何为什么还看不到落值**：我们建的容器不在任何被刷新的树上（自建屏幕没被 load、也没挂到活页），
LVGL 不会为它跑 layout，所以 `coords` 一直是初始值。`page2` 里四个属性都调成功了（对象 `+0x2C` 的
local-style 标志从 `0x210000` 一路涨到 `0x610000`），但对象内存里找不到 300/200/10/20。

⇒ 要坐实"几何真的生效"，得先拿到**活页的根对象**，把控件挂进那棵树，等 UI 线程刷新后再读 coords。
这正是下一步：活页根（页栈条目 `0x3C4940E0` / 页实例 `0x3D27xxxx` 那一片）还没有可靠取法。

### 16) `app_install` 的断言终于读准了：**空键**，不是"表为空"

`clone2`（克隆 app 19 的记录、换成我们自己的两个回调）重跑，QMP 现场：

```
R0=0x3C340A90  R1=0x93(=147)  R2=0  R3=0x3D480680
LR=0x0CA3BB81  PC=0x0C4F74E8(断言哨兵)  XPSR=priv-thread（不是异常）
```

`R0` = 串 `"util/hashmap.c"`（file 0x370854；它的字面量引用就在 0x97BAB4..0x97BCFC 这几支里）。
反编译 `FUN_0097BAB8(map, key, …)`：

```
if (map == 0)      -> 断言（146 行）
if (key == 0)      -> 断言
if (key[0] == 0)   -> 断言（**147 行** —— 正是本轮的 LR 落点）
```

⇒ **不是"哈希表未初始化"，而是查表时键是空串**。也就是说 install 走到"按某个字符串键登记"那一步时，
那个键在本机是空的（与 `/system` 没挂上、应用模型根路径没填同一类环境缺口）。
这同时解释了早先"表为 NULL"的读法为什么对不上：`map` 非空、`key` 空。

**含义**：`app_install` 本身没有坏，坏的是本台 guest 的应用模型环境。要真正验它，得让 `/system` 挂上，
或者把那个键补出来（下一步：从 `LR=0x97BB80` 的调用者 `0x97BF88 / 0x73A9A8 / 0x734CA0` 里找出键的来源字段）。

### 17) `page_goto` 的崩因也不是"上下文"：**它自己在 `mm_free` 里断言**

`goto2`（主循环定时器回调里调 `page_goto(1,0,0,0)`）重跑，QMP 现场：

```
R0=0x3C181830  R1=0xFC(=252)  R3=0x3C57FB80  LR=0x0C50A641  PC=0x0C4F74E8(断言哨兵)
R6=0x3C450030  R8=0x3C4500B4(定时器链表)  R10=1  R11=0xFFFFFFFF
```

`R0` 指向的串（file 0x1B15F4）= **`mm_heap/mm_free.c`**，`R1=252` ⇒ 崩在 **NuttX 堆的 free 断言**里
（释放了一个不属于该堆/未分配的指针），不是页面逻辑、也不是"必须在 UI 线程"。

⇒ 两条旧结论作废/修正：
1. "在 NSH 线程调 page_goto 会崩" —— 真因不在线程；
2. "需要主循环上下文" —— 主循环里调**同样**崩，崩点还是同一支 free 断言。

**可能的解释（待验）**：这一发的参数 `start_data=0 / callbacks=0` 让切页路径去释放一个
本机页面状态里并不存在的对象（当前 setup 页的页实例只有半截：页节点 `+0x24/+0x30` 全 0）。
下一枪要么带真实 `start_data`（照 043 调用点抄），要么先补出当前页的实例对象。

**顺带记一条取证口径**：断言现场 `R0` = 源文件名串、`R1` = 行号，把 `R0` 按 `VA−0x3BFD023C` 换成 file
偏移再读串，就能直接认出断言所在文件（本轮靠它一眼看出是 mm_free 而不是 lvx 页面）。

### 24) `lv_obj_add_event_cb` 执行确认（不靠事件触发，看登记）

`evt` 探针：建 label + `add(o, 我们的回调, 7, 0xBEEF)`，然后**全 PSRAM 搜 0xBEEF**：

```
0x3C6AC2F4 附近：… 0x3D49BC09(回调) 0xBEEF(user_data) 0x7(filter)
```

⇒ **`lv_obj_add_event_cb = 0x0C2570BD`（file 0x1970BC，跳转壳 → SRAM `0x00388099`）**，
事件描述符布局：`+0x0C = cb`、`+0x10 = user_data`、`+0x14 = filter`（三条都是我们传进去的原值）。
对象自己的事件数组挂在 `spec_attr` 旁（本例描述符在 `0x3C6AC2E4`，label 的 `spec_attr` 是 `0x3C6AC2F0` 一带）。

这一步顺带给了事件侧的两个口径：
- 判定"登记成功"不必等事件；搜 `user_data` 这个魔数就够（**执行级证据**）。
- 描述符里 `+0x10` 是 user_data、`+0x14` 是 filter；加上此前从分发器读到的"事件结构 `+0x08 = code / +0x0C = user_data`"，
  回调里可以直接读这两格，不依赖 `lv_event_get_*`。

### 26) 更正：文本属性号不是 0x40..0x42，是 **0x58..0x5E**（TEXT_FONT=0x5A）

第 13 节那张表里"TEXT_COLOR=0x40 / TEXT_OPA=0x41 / TEXT_FONT=0x42"是**按常见枚举顺序猜的，错的**。
043 侧有逐字节实证：`row_init` 与字体 getter 都以 `movs r?, #0x5A` 取 text_font，
`gfx.rs` 的 `LV_STYLE_TEXT_FONT` 常量也是 0x5A（那条在真机跑过）。文本块整段在 **0x58..0x5E**：

```
0x58 TEXT_COLOR   0x59 TEXT_OPA   0x5A TEXT_FONT   0x5B TEXT_ALIGN
0x5C TEXT_LETTER_SPACE   0x5D TEXT_LINE_SPACE   0x5E TEXT_DECOR
```

旁证：`lvx_page_title_create` 里两个 `set_local_style_prop(obj, 0x5C, ...)` / `(obj, 0x63, ...)`
的薄包装（影子源 file 0x19450 / 0x194C8，函数体只有一条 `movs r1,#0x5C|#0x63; b funnel`）。

**教训**：属性号不许按枚举顺序推，必须从固件自己的 setter 里抠（第 13 节的做法），
并且拿 043 已在真机验证过的常量做交叉核对。

### 27) 调用口径：跟着固件走，别自己拼别名

这一轮踩到的（都复现过）：

| 目标 | 固件怎么到 | 正确调法 |
|---|---|---|
| file 0x6CC878 `lv_label_set_text` | 直接 `bl`（flash-only 段，file > 0x2FDC4） | **XIP `0x0C78C879`** ✓ |
| file 0x115D4 `create_obj` | 跳转壳 → SRAM `0x003775BD` | 调**SRAM 真身** ✓；走 XIP 壳会返回 `0x5D` 这种非指针 |
| file 0x1297C 样式漏斗 | 跳转壳 → SRAM `0x00378965` | 调壳或 SRAM 真身都行 ✓ |
| file 0x17640 样式 getter | 被 `FUN_000127ac` 直接 `bl` | 试 XIP `0x0C237641` → **UsageFault**；它落在 file < 0x2FDC4 的那一段（早期代码），XIP 别名不可执行 |

**规则**（写进探针注释）：函数在 **file ≥ 0x2FDC4** 的段里 → XIP 可直接调；
file < 0x2FDC4 或固件经跳转壳/SRAM 到达的 → 用 `scripts/p65_thunk_resolve.py` 解析出的
**真身（SRAM/RAMX）**；不要自己拿 PSRAM 增量去套——file < 0x2FDC4 根本不在 PSRAM 拷贝段里
（拷贝从 file 0x2FDC4 开始，那是 `0x3C000000`）。

另：**连续跑多档探针会把 NuttX 堆耗光**（`mm_heap/mm_malloc.c:333 Allocation failed`），
之后所有"再建一个对象/定时器"的探针都会假崩。**每跑 5~6 档就 kill+start 一次**。

### 28) 样式 getter 找到真身，但回读没取到值（WIDTH 仍待验）

`lv_obj_get_style_prop(obj, prop, &out, selector)` = file 0x17640，**SRAM 真身 `0x2017D628`**
（把 file 0x17640 起 24 字节在 SRAM dump 里搜到；RAMX 别名 `0x0037D629`，与 `add_state` 同段）。
反编译：找对象样式表里 selector 匹配的那条 → `bl 0x2F328`（`lv_style_get_prop`）写 out；
找不到直接 `return 0`。

`getw` 探针（`set(o,1,300,0)` 后 `get(o,1,&v,0)`）：**不崩，但 `v` 仍是 0** ——
getter 报"没这条属性"。两种可能：① `WIDTH=1` 不对（但应用层确实用 1 当宽度，`lvx_page_title_create`
里 `(obj,1,0x2A,0)` 就是设宽）；② selector 传法不对（可能要 `part<<16|state` 而 `0` 没命中）。

⇒ **WIDTH=1 仍列待验**；下一步用"两段式 selector（如 `0x10000`）"再打一枪，或直接读本地样式表比对键。

**getter 续测（`getw2`）**：连"读 label 的主题字体（prop 0x5A）"都返回 0 —— 说明**不是 WIDTH 的号错**，
而是这支 getter 在我们这条调用路径上取不到任何属性（`[obj+0x32]` 的样式计数非 0，但按 selector 一个都没匹配上；
探针里样式表的 selector 字段实测是 `0x01000000` 这一档，与我们传的 0 对不上）。
⇒ 结论：**getter 的 selector 约定还没吃透**，先不拿它做判据；`WIDTH=1` 仍按"应用层用法 + setter 序列"记为静态证据。

### 29) `lv_image_set_src`（静态定案）

### 31) 定时器另外两支

- **`lv_timer_delete(timer)` = `0x0C74154D`**（file 0x68154C）：`ll_remove(&timer_ll, timer)` + `lv_mem_free`。

### 39) 样式漏斗的身份定案（推翻 §30 的 0x00378965）

此前把 **0x00378965** 当成 `lv_obj_set_local_style_prop`，用它设宽高/底色/字体，桌面上只出现一块白 ——
根因不是"渲染通道没有"，而是**那一支根本不是通用 setter**。逐字反编译（影子源 file 0x1297C）：

```
FUN_0001297c(obj, a, b, c):
  FUN_00018de8(obj, a, 0)      ; 属性 0xA
  FUN_00018db8(obj, b, 0)      ; 属性 0x8
  FUN_00018dd0(obj, c, 0)      ; 属性 0x9
```
三支属性包装各自先 `mov ip, r1` 把 value 暂存进 r12，再 `movs r1,#N`、`mov r2,ip`，
最后 `bl FUN_00018420`。三支都是"先查同属性现值、不同才写"。所以它是
**`lv_obj_align(obj, align, x_ofs, y_ofs)`**：只写 align/x/y，宽高和颜色一概不碰。
（Ghidra 反编译里缺了函数首字的 `mov ip,r1`，看着像 `mov r2,r12` 的怪指令，用 capstone 读字节才对上。）

通用漏斗是 **FUN_00018420**：在 `obj+0x0C` 的本地样式数组里按 selector（`style+4 & 0xFFFFFF`）
找/建条目，`FUN_2f380(style, prop, value)` 写属性，再按 `prop>>3` 置 `obj+0x10/+0x14` 的脏位，
最后 `FUN_17d6c(obj, prop, selector)` 刷新。
活体地址（SRAM 副本，file 0x18420 起 24 字节在镜像里唯一命中）：
**`lv_obj_set_local_style_prop = 0x0037E409`**；
配套取值入口（file 0x17640）**`lv_obj_get_local_style_prop = 0x0037D629`**，
返回 1 = 命中并把值写进 `out[0]`。

### 40) 样式属性号：043 的组 0 在 p65 不适用（逐属性对照实测）

做法：一属性一个对象，各自只写一个可区分的小值（`0x30 + i*8`），宿主侧读 `obj+0x1C..+0x28`
的 coords。

| 写的属性 | 值 | 结果 coords | 结论 |
|---|---|---|---|
| 1 | 0x38 | 宽 = 0x38 | **WIDTH = 1** |
| 2 | 0x40 | 高 = 0x40 | **HEIGHT = 2** |
| 3 | 0x48 | 130x130 | 无影响 |
| 4 | 0x50 | 130x130 | **043 的"HEIGHT=4"在这里无效** |
| 5 | 0x58 | 宽 = 0x58 | 夹取上界，未定名 |
| 6 | 0x60 | 130x130 | 无影响 |
| 7 | 0x68 | 高 = 0x68 | 夹取上界，未定名 |
| 8 | 0x70 | x1 = 0x70 | **X = 8** |
| 9 | 0x78 | y1 = 0x78 | **Y = 9** |
| 0xA | 0x80 | 130x130 | ALIGN（静态：`lv_obj_align` 第一支写 0xA） |
| 0xC | 0x90 | 130x130 | RADIUS（静态：主题样式 0xC=10 与渲染圆角一致） |

**不设宽高时建出的 `lv_obj` 是 130x130** —— 这是主题给的默认尺寸，每个容器都必须显式设 W/H。

其余已执行确认的组：
- 底色/不透明度：`0x1C` / `0x1D`（设 0xFF0000+0xFF 整块纯红；设 0x00FF00 变绿）。
- 文本：`0x58` 颜色、`0x59` 不透明度、`0x5A` 字体（`"Chaos"` 用 MiSans 24 渲染成 69x32、
  设 0xFF0000 变红）。
- 内边距：`0x10..0x15`（主题对 `lv_obj` 设的是前四个 20、后两个 11）。**子对象坐标从父对象的
  内容区起算**，所以容器不把 `0x10..0x13` 清零，子对象会整体偏移 20px。


页描述符注册后的实际内容（宿主 QMP 读）：

```
+0x00 0x3C3CF5C0   页节点（固件填的）
+0x10 "chaosmain"  页名
+0x14 0x77770000   页键 = app_id<<16 | 页序号（序号从 0 起）
+0x2C 0x3C3CF53C   页管理器（固件填的）
+0x34/+0x4C/+0x50/+0x58/+0x5C/+0x60  六支回调，全是我们模块里的函数
```

三条把这条路堵了很久的实现错误，逐条记下来：

1. **`app_install` 的第二个参数是"页描述符指针数组"**（每格放描述符地址），不是描述符本体。
   直接传 `PAGE.as_ptr()` 时，固件把描述符第一个字（0）当成页指针：页注册被跳过、应用页数组里
   `arr[2] == 0`，之后从桌面点开就崩在 **`util/hashmap.c:147` 空键断言**
   （R0=`"util/hashmap.c"`、R1=147、PC=0x0C4F74E8）。改成
   `let items: [u32; 1] = [PAGE.as_ptr() as u32]; install(desc, items.as_ptr(), 1)` 之后，
   `arr[2]` 立刻变成描述符地址，点开不再崩。
2. **页描述符不能克隆系统应用的**。克隆会把对方的页节点（`+0x00`）、页管理器（`+0x2C`）、
   链表指针（`+0x40/+0x44`）带进来，固件碰别人的对象必崩。正确做法与 043 一致：
   **116 字节全零**，只填 `+0x10` 页名、`+0x14` 页键、`+0x34/+0x4C/+0x50/+0x58/+0x5C/+0x60`
   六支回调；页节点与页管理器由固件的注册函数自己填。
3. **应用图标是 112x112 的 LVGL bin**（12 字节头 `19 10 00 00 70 00 70 00 C0 01 00 00` + BGRA），
   不是 PNG。用 `Chaos-Module/tools/gen_chaos_icon.py` 生成后传到 `/data/chaos_icon.bin`，
   应用描述符 `+0x0C` 指这个路径即可。桌面图标会正常显示成 Chaos 的蓝色六边形。

遗留观感问题：**打开我们的应用没有进场动画**（系统应用有），关闭有退出动画。
页描述符注册后 `+0x28` 是 `0x00020404`，app 19 的是 `0x00020504` —— 差的那一位很可能就是
进场动画/转场类型，待逐位核对。

```
     headers: X-MiBand-Control: <token>, Content-Type: application/json, Origin/Referer: <manager base>
```

判据与用法：
- 在表盘上 `click` 一次 = 按表冠 → **直接打开应用列表**；在应用列表里 `click` 一次 = 返回表盘。
- `rotate` + steps 在列表/表盘里滚动。
- 关卡内点击（选中图标）仍用 QMP `abs`+`btn`（短按 80~120ms）。这套组合不需要用户代点。

两条与"卡死"有关的现象，记下来省得再误判：
- **画面停在最后一帧不等于活着**。`screendump` 15 秒超时 + NSH `503` 就是挂死
  （内存还在、界面不再响应）。判活要同时看 `/api/machine` 的 runDir 与一次成功的截图。
- `page_goto(0x77770000,0,0,0)` 即使页已正确注册，**仍然把整机挂死**（mark 写不上、
  随后 NSH 503）。这条在 RW6 上不要再用；页内跳转要靠固件自己的入口。

### 47) 原生行的候选构造 0x0C83B4C1 是错的（会把 UI 挂死）

按形状配对挑出来的 `0xC83B4C1`（file 0x77B4C0）当 `row_create` 用，`on_create` 里一调，
整页挂死。它是系统"活力指标"页里的一个卡片构造，不是列表行。原生列表行的入口还没找到；
`sports` 页（`com.xiaomi.miwear.sports`，页名 `page_home_list`）的 `+0x4C` 不是 UI 构建函数，
从它身上也拿不到行构造。

下一步找行控件的正路：**从系统设置页的 `on_create` 往下找**（设置不在注册表里，是系统 UI 页），
或者按 043 `row_create` 的**调用点**（043 侧唯一调用者是设置页 `FUN_004901e0`）在 p65 找同形调用序列。

### 48) 图标要排进网格，必须在**屏幕醒着**的时候挂

同一份 `launcher_add`，在屏幕休眠时调只会建出记录与图标对象，**对象坐标停在 (0,0)-(0,0)**，
网格不排版；屏幕醒着时调，图标对象立刻拿到真实坐标（实例：(329,210)-(423,304) 96x96，
父对象是桌面页）。

可复现的自测顺序（不需要真人）：

1. 等 guest 就绪 → 上传模块（不要先 insmod）；
2. `POST /api/crown {"action":"click"}` 唤屏并打开应用列表；
3. 立刻 `insmod`（模块第 1 秒调 `launcher_add`，此时屏幕是醒的）；
4. 3 秒后读桌面记录链尾 `+0x10` 图标对象的 coords —— 有真实坐标就说明排进网格了；
5. 用 QMP `abs`+`btn` 在图标中心短按一次，读模块结果通道里的 `on_create` 标记。

踩到的两个坑：屏幕休眠时挂图标不排版（上面这条）；`page_goto` 与猜出来的行构造
（`0x0C83B4C1`）都会把整机挂死，不要用。

### 49) 桌面图标的事件回调与「打开应用」入口（静态）

桌面记录 `+0x10` 的图标对象，`spec_attr+0x08` 是事件表 `{dsc 指针数组, 条数}`；我们的图标上有两条：

```
dsc[0] { cb=0x0C7EFB29, ud=0,      filter=0x15 }   // 删除类
dsc[1] { cb=0x0C7EF9C5, ud=0x7777, filter=0x04 }   // 点击类，ud 就是 app_id
```

`0x0C7EF9C5`（file 0x72F9C4）逐段读法：

1. `FUN_0067d8e4(e)` 取事件码；码在 `0x16..0x3E` 或等于 `0x46` 时走别的分支/直接返回。
2. 取事件里的 `user_data` 当 **app_id**，经注册表 `[[0x72FAF4]+0x18]+4` 取节点。
3. 节点为空返回；**节点 `+0x12` 的 bit2 置位也返回**（这是"该应用不可打开"的那一位）。
4. 调 `节点+0x1C`（显示名回调）拿名字，做一次比较，然后在一个 0x2C 的栈结构里填
   `{+0x00 名字, +0x0C app_id, +0x18 ?, +0x1C ?}`，最后经 `[[0x72FB08]+4]`（vtable）
   **真正打开应用**。

⇒ 进场动画与页切换都在最后那一发 vtable 里，是固件自己的路径。下一步二选一：
一是找到 `lv_obj_send_event(icon, LV_EVENT_CLICKED, NULL)` 直接触发这个回调（最稳，等同于真点击）；
二是照抄这一发的 vtable 调用参数顺序直接调。两者都要先用 `node+0x12` bit2 确认我们的节点是"可打开"的。

### 50) 两个负结果：`lv_obj_send_event` 那格与"按坐标点图标"

- **`0x0C73D62B` 不能当 `lv_obj_send_event(obj, code, param)` 用**：在第 40 拍对桌面图标对象发
  `(icon, 7, 0)`，guest 当场挂死（随后 NSH 503）。手拼事件结构那次的崩也是同一族问题，
  这条入口在没有确定签名与事件结构约束前不要再点。
- 按"内存里读到的图标中心"点图标：本轮第 1 次点的是 y≈493 的槽位（与底部「布局切换」按钮重叠），
  guest 随即挂死；说明这个位置的命中对象不是图标。要点图标必须先用它的 coords 确认落在网格区内
  （y 上限留出底部按钮带），并且点之前屏幕是醒着的。

下一步改成：唤醒后 insmod，**先读图标 coords，确认在网格区**再点；点完立刻读 `PROBE_RET`，
不额外截屏（截屏在这台 guest 上经常和挂死混在一起，干扰判断）。

### 54) `vtable[2]`（0x1C134189）也不是"打开我们的应用"：它打开了桌面

按点击回调里打开那一支的入参形状（struct1 +0x06 code、+0x08 =1、+0x14/+0x20 两个回调、
+0x18 指向 nested、+0x34 =0x33；nested +0x08 =0x33、+0x1C/+0x20 为坐标）手工拼装并调用
`0x1C134189`：**返回 1、guest 不复位**，但界面打开的是**桌面**（20 个系统图标），
我们的页没有被建（`on_create` 一直为 0）。

⇒ 该槽只负责"回到/切到桌面"这一层；真正的"打开某个应用"还需要把**应用/页**的交待字段
填对（大概率是 struct1 里我们还没敢填的 `+0x00/+0x04/+0x0C` 或 nested 的其余字段）。
在把点击回调那一支**逐条**读全（含它引用的两个 PSRAM 回调干嘛）之前不再猜字段。

### 67) 主菜单 + 应用管理页：真实应用列表（名字/编号来自桌面记录链）

`work/p65_chaos` 现在是三页：主菜单 / 关于 / 应用管理。实测（`build/shot_y1_menu.png`、

名字与编号都是从桌面记录链现读的：记录 `+0x04` 是名字串指针、`+0x00` 低 16 位是 app_id、

1. **名字截断**：按缓冲长度截断后才需要回退到 UTF-8 字符边界。无条件回退"尾部续字节"

   `app_at()` 里的 `cut` 标志；
2. 记录链的**顺序由固件维护**，不是固定安装序（同一台 guest 上翻几页会看到前缀变化）。
   要稳定排序就得自己按 id 排，但那就不是系统顺序了；目前按系统顺序展示。

点击语义（回调只写槽、重建在 tick 里）：
- 主菜单：0=应用管理、1=关于、2=不动；
- 关于页：任意行回主菜单；
- 应用管理：第 5 行（下一页/上一页）翻 4 条，末尾回卷。

**试过又撤掉的一条**：点应用行直接 `open_app_id(id)` 把别的应用拉起来。实测点「录音机」
之后整机黑屏并复位（同一发 `OPEN_APP` 用本应用 id 是好的）——打开第三方应用还要别的
前置（或者是这台 guest 缺应用资源），先不做，别把它当"顺手就能加"。

### 68) 行控件换成系统原生卡片 + 系统标签（原来那版是自绘）

用户看图后判定「控件都是自己绘制的，不像 10P 那样用系统控件」。查清 10P 侧的实情：
10P 是**一发 `lvx_list_row_create(parent, primary, secondary, trailing)`** 建行，
行内标签、右端部件、底色圆角字号全由固件给；我们只填文字、挂事件、对齐
（`fw_api/page.rs:16`、`page.rs:102` 的 `obj_align_to(row, prev, 14, 0, 8)`）。

p65 没有同名的一发式入口，但**系统「设置」页那条原生行就是 p65 的等价物**，
整条构建次序从固件代码里抄了出来（`fw/p65_100_043` file `0x64a30` 那一段）：

```
建卡片            0x00387B79   （RAMX 别名，系统的"建容器"）
尺寸 416x120      0x0C255CE5
底色 0x222222     0x0C257B3D
内边距 32         0x0C256665
位置 (8,y)        0x0C2568ED
清样式/标志       0x0C258025 / 0x0C2583B5 / 0x0C25758D / 0x0C256455
事件(码7)         0x0C2570BD
属性 0x30 清零    0x0C256765
卡片整体样式      0x0C92E9C5
建系统标签        0x0C78BCB5   （内部：按类建对象 + 初始化两发）
设尺寸/位置       0x0C255CE5 / 0x0C2568ED
设文字            0x0C78C879
主样式/副样式     0x0C21E581 / 0x0C21E089
标签标记          0x0C78C995
```

关键三条（都踩过）：
1. **系统标签是两发**：只 create 再 init。走我们那个 `create()`（create+init）等于
   **初始化两次**，一建标签就挂（STEP=2 崩在这里）。改成直接调系统那一发
   `0x0C78BCB5` 才好。
2. **底色是 0x222222 不是 0x2222**：写 0x2222 会渲染成 `(0,34,34)` 的青。
3. **flag 是位掩码**：CLICKABLE=0x2、SCROLLABLE=0x10。给页面加 `0x10` 才有滚动；
   误加 `0x5`（=HIDDEN|CLICKABLE）整页变黑。

白边/外框的来由与清法：类默认样式带一圈浅色描边（`(224,224,224)` 两像素），
系统建完卡片会清掉。逐个属性试无效（那几发是通过函数指针派发的间接跳转，
Ghidra 看不到目标），最后按框架的 **prop 名字表**（PSRAM `0x3C34ACB0` 起，名字按
属性号排开，`text_color=0x58`/`text_opa=0x59`/`text_font=0x5A` 与实测一致可当锚）
整段清 `0x14..0x57` 才清掉。注意整段清会把**本地 bg 清成透明**（本地优先级高于
样式表），要再把本地 bg 补回来。

实测结果（`build/shot_lay6_apps.png`）：系统原生卡片、灰底圆角无描边、系统大号白字
标题 + 灰色编号副行、页面无外框、标题栏是系统原生的。翻页行改成 56 高的紧凑卡片
（120 高的放 y=452 会超出屏幕底，点不到）。

一条没走通的：`FUN_0017f90c`（系统那层自带滚动的内容容器）在我们的上下文里一调就挂，
应用都打不开。系统把行挂在那一层里面，我们暂时用页面自身当容器 + 加 SCROLLABLE 标志。

### 69) 行一次建完 + 页面能滚（对照系统设置 App 的真实结构逆向）

用户看完又提三条：行是一点一点冒出来的、页面不能滚、打开应用没动画。三条都按

### 71) 时间：三个候选锚点，两个不可用

Chaos 的招牌是「时间·日期设置」页。p65 侧查了三条：

| 锚点 | 出处 | 结果 |
|---|---|---|
| `0x0C4C21DC` get_time_raw | file `0x4021DC`，内部 `FUN_0041A534` 从 ops 表取时钟源，值域 100 微秒 | **返回 0**（ops 表在 guest 里没填）。而且它是「看门狗用的递增计数」，不是日历时间 |
| `0x0C615569` NuttX clock_gettime | file `0x455568`，内部 `up_clock_gettime(CLOCK_REALTIME=0, &ts)`，失败串 `clock_gettime(CLOCK_REALTIME) failed` | **失败即 panic，把整个 guest 带崩**（NSH 也不再响应） |

不是秒，别当秒用。

**结论**：p65 的日历时间入口还没找到，先不做「时间」行，别拿会 panic 的入口去试。

### 72) 全链路打通：桌面图标 -> 点开 -> Chaos 页（系统转场）

### 76) 文件能力打通：VFS 三支入口（open/read/close）执行确认

**入口来源**：nsh 的 `cat` 实现 `nsh_catfile`（file `0x4F0C98`，由 `cat` 的参数解析
`FUN_004F127C` 调过去）里三条调用逐条读出：

| 用途 | 运行地址 | 调用形状 |
|---|---|---|
| open | **`0x1C15_80E4`** | `open(path, 1)` —— 只读标志是 **1**，不是 POSIX 的 0 |
| read | **`0x1C15_8720`** | `read(fd, buf, 0x400)` |
| close | **`0x1C15_4D9C`** | `close(fd)` |

三个都在 PSRAM 代码段（`0x1C15xxxx`），当函数指针用时 `|1`。**不要从符号表找**
（modlib 不导出 libc，见下），也不要按 `open\0` 串反查（镜像里没有指向它的 32 位字面量）。

**执行验证（最小探针，不开页面）**：定时器第 60 拍调一次
`open("/proc/meminfo",1)` → `read(fd,buf,64)` → `close(fd)`，结果写 DIAG：

```
DIAG[20]=0x0BEE0001  DIAG[21]=0x5A(=fd 90)  DIAG[22]=0x0BEE0002
DIAG[23]=0x40(=64B)  DIAG[24]=0x20202020（/proc/meminfo 行首四个空格）
DIAG[25]=0(close)    DIAG[26]=0x0BEE0003（走完，没崩）
```

**整页验证**：默认构建（`default = ["procfs"]`）重新开机装载后主页五行的截图
`build/shot_pg_home.png`：

```
内核 p65 3.100.043     内存 15M/21.5M     存储 24.8M/291.4M     应用管理 40 个     关于
```

内存取 `/proc/meminfo` 的 `Umem:` 行（used/total），存储取 `/proc/fs/blocks` 的 `/data` 行
（block size × used / block size × blocks）。这两组数与 NSH `cat` 的输出逐项对得上。

**注意上下文**：回调用的是 LVGL 定时器（UI 线程），那里有可用的文件描述符表；
换到别的线程要用新的探针复核，别默认同一结论。

**本轮走过的弯路（别再重复）**：
1. **符号表里没有 libc**：扫 SRAM 全部 4 字节值、把指向 PSRAM 串池的都解出来比对，
   `open/read/close/ioctl/lseek/printf/statfs` 零命中；镜像里也没有指向 `open\0` 的地址。
2. **异常/中断链路不是入口**：运行期向量表在 SRAM `0x20166000`（96 槽），SVCall 槽 11 =
   `0x0C514A19`；它做上下文保存（file `0x44DAD8`）后经 `file 0x454560` → veneer 表
   （file `0x7FC7F0` 起，每项 8 字节 `ldr.w pc,[pc,#0]` + 目标）跳到 `0x36F389`
   （SRAM `0x2016F388`，flash 源 = **file `0xB8A0`**）。`FUN_B8A0` 是按号查 8 字节表
   {handler, arg} 的分发器，表在 SRAM `0x201734B0`，槽 11 落在链表删除函数上
   —— **它不是 syscall 分发表**。
3. **日志 tag 不是 `__func__`**：`"fs_open"` 串（VA `0x3C20B98C`）被 file `0x675848`
   的日志包装函数（`FUN_00674F60` 调 `FUN_0067E32C` 打 level/line/module）当 tag 用，
   不能拿它反推函数边界。
4. **rebuilt PSRAM blob 不能反查 xref**：`/data/app/launcher/launcher.db`（blob file
   `0x23E76C`）按 `0x1C+off / 0x3C+off / 纯 offset` 三种口径搜引用全部零命中
   —— blob 是重建产物，重定位痕迹没了。

### 77) 目录遍历：`open` 打不开目录，要另找 opendir

NuttX 的目录不能用 `open` 当文件打开。实测（探针，路径 `/data/app`）：
`open(dir, 1)`、`open(dir, 1|0x20000)`、`open(dir, 1|0x10000)`、`open(dir, 1|0x8000)`
**四个都返回 -1**。文件 `/proc/meminfo` 用同一个入口正常（fd=90），所以不是入口问题，
是目录必须走 `opendir/readdir/closedir`。

**VFS 三支在 AP 镜像里的源地址**（把活体 PSRAM 前 32 字节回查镜像，唯一命中）：

| 用途 | 运行地址（PSRAM） | AP file | 反编译结论 |
|---|---|---|---|
| open | `0x1C15_80E4` | **`0x187EA8`** | `nx_vopen`：先 `FUN_00187AE8` 解析路径/inode，再 `FUN_001840C4` 分配 fd |
| read | `0x1C15_8720` | **`0x1884E4`** | `nx_read`：`FUN_001844C4` 取 file → `mops->read`（inode+0x10 → +8） |
| close | `0x1C15_4D9C` | **`0x184B60`** | 释放 file 表项并回收 |

也就是说 **VFS 就实现在 AP 镜像的 file `0x184xxx~0x188xxx` 这一段**（拷到 PSRAM 执行）。
下一步找 `nx_opendir/nx_readdir/nx_closedir` 的抓手：
① 同一段里按签名扫（`nx_opendir(path, DIR**)` 会调路径解析 + 目录分配）；
② 从 JS 运行时的 `jse_file opendir failed`（串在 file `0x31D3F2` 一带）反查调用点，
   那支的 callee 就是 opendir。
拿到之后：表盘列表、缓存清理、字体/图标清单这三类功能一起解锁。

```
fp+0x14 = 0x3D4A9D70   目录状态指针（推测 f_priv）
```

inode+0x10 指向的表（PSRAM `0x3C2B0EC4`）只有前 5 项是代码指针，后面就是字符串
（`fvs/fs_y…`）。映射回镜像：

| 槽 | 运行地址 | 镜像 file | 判读 |
|---|---|---|---|
| +0x00 | 0x1C159E39 | 0x189BFD | yaffs open |
| +0x04 | 0x1C159AE9 | 0x1898AD | close |
| +0x08 | 0x1C159C59 | 0x189A1D | read |
| +0x0C | 0 | — | write（本挂载只读，空） |
| +0x10 | 0x1C159B4D | 0x189911 | seek |
| +0x14 | 0x1C159AB9 | 0x18987D | ioctl |

⇒ **这张是文件的 file_operations，不是挂载点的 mountpt_operations，里面没有 readdir**。
目录遍历要走 `opendir/readdir/closedir` 那一族（挂载点 ops 或 libc 层），不能从 inode 上这张表拿。

**重要口径修正**：VFS 代码在 PSRAM，`运行地址 = file + 0x1BFD023C`（不是 file+0x0C0C0000）。
先前两次把 file 偏移当运行地址调 `getfile`（0x001844C4）⇒ 未映射地址，直接把 guest 打崩；
修正成 `0x1C154700` 后 dump 正常。**以后所有 PSRAM 函数一律先换算再当函数指针用。**

### 80) 目录遍历打通（执行级）：opendir/readdir/closedir 三支

**入口怎么找到的**（这条链值得记）：`/proc/meminfo` 串只是 nsh `cat` 的用法示例 →
`cmd_cat`（file 0x4F127C）→ `cmd_ls` = **0x0C5B02B5**（file 0x4F02B4，由命令表项
`{name, handler, args, usage}` 定位：`ls` 的 name=`0x3C19E33C`、handler=`0x0C5B02B5`）→
`cmd_ls` 对目录调 `nsh_lsdir`（file 0x4F0F8C）→ 里面三条：
`opendir`(0x437884) / `readdir`(0x4378EC) / `closedir`(0x4378C0)。

| 用途 | 运行地址 | 说明 |
|---|---|---|
| opendir | **`0x0C4F_7884`** | malloc(0x68) 当 DIR，再 `open(path, 0xC01)`（O_RDONLY 1 + 0x400 + O_DIRECTORY 0x800） |
| readdir | **`0x0C4F_78EC`** | `fd = [DIR+0]`、entry = `DIR+4`（0x62 字节），返回 entry 指针或 0 |
| closedir | **`0x0C4F_78C0`** | close(fd) 后 free(DIR) |

**dirent 布局实测**：`d_type @ +0`（DT_DIR=4 / DT_REG=8）、`d_name @ +1`。

**执行验证**：探针 `opendir("/data/app")` → 连续 8 次 readdir → closedir，返回 0；
8 条依次是 `fusion(4) / watchface(4) / phone(4) / home(4) / media_manage_data.bin(8) /
nfc(4) / system_*(4) / sport(4)`，与 NSH `ls /data/app` 完全一致。

⇒ 表盘列表、缓存清理、字体/图标清单、文件浏览这四类页面现在都有底层能力了。
（注意：`/data/app/watchface/watchface.db` 在这台 guest 上不存在，`cat` 报 open failed 2，
 表盘清单要走目录 `builtin/`、`market/`，不要按 DB 路径写死。）

**删除入口（静态确认，尚未执行验证）**：nsh 命令表里 `rm` 的处理器 = **0x0C5B07F9**（file 0x4F07F8）。
它对普通 `rm <path>` 调 **`unlink = 0x1C159914`**；`rm -r` 走另一个递归助手
（`func_0x004EF8A0(path, ...)`，名字未定）。表项布局再次自证：`{name, handler, args, usage}`
16 字节，`rm` 的 name=`0x3C212BEC`。

这一支的**执行验证没做成**：探针源码里 `\0` 的转义被写成了真 NUL 字节（文件一度变二进制），
模块里探针也没按预期在 tick 60 触发，两次跑完文件都还在。已把源码恢复干净（NUL 清零、
探针删除），下一轮用编辑工具写探针 + 单模块干净环境再验一次，再据此做缓存清理页。

### 81) 缓存清理页落地：unlink/rmdir/fstat 三锚点执行级验证 + 增量清理

**三个文件锚点**（PSRAM 里的 VFS，运行地址 = file + 0x1BFD023C；本节三个都已在
MiBand Studio 的 redmi-watch6 guest 里跑过执行验证，不是静态推断）：

| 用途 | 运行地址 | 文件偏移 | 执行验证读数 |
|---|---|---|---|
| unlink | `0x1C15_9914` | 0x1896D8 | 返回 0，`cat` 报 ENOENT，文件真消失 |
| rmdir | `0x1C15_8B08` | 0x1888CC | 返回 0，`ls` 报 stat failed 2，目录真消失 |
| fstat | `0x1C15_7650` | 0x187414 | 返回 0，stat 的 `+0x18` 是字节数（探针文件 11 字节读回 11） |

找法：`rm` 的命令表项（handler `0x0C5B07F9`）里对普通文件调的就是 unlink；
`rm -r` 的递归助手（`0x0C5AF8A0`）在读完子目录后调 `0x0C8BBE78`（那是
`ldr.w pc,[pc,#0]` 的跳转壳，落到 PSRAM `0x1C158B08`）删空目录。
fstat 是从 stat 族候选里逐字读出来的：`0x1C157650` 先 getfile 再 `0x1C15752C` 填 stat，
后者明写 `str r3,[r6,#0x18]`（大小）与 `movw r1,#0x91b6`（mode）。

**执行验证怎么做才算数**：探针模块在 tick 60 做一次删除，删前用 NSH
`echo hellochaos > /data/chaos_probe.txt` 造文件（echo 会补换行 ⇒ 11 字节，
与 fstat 读回的 11 对得上），删后用 NSH `cat` 复核"open failed: 2"。

**踩到的两个坑（都改变了做法）**：

1. **旧探针模块还挂在系统里会抢答**。NuttX 对同名 insmod 直接 EEXIST，
   但**不同名**的旧模块照样在跑各自的 tick。第一轮读数是 unlink 返回 -1，
   真因是上一轮装的那个模块先一步把文件删了，这一轮撞上 ENOENT。
   ⇒ 单次锚点验证前必须 `rmmod` 掉旧探针（或整机重启），只看返回值会得出
   "unlink 不好使"的错结论。**判据：以"文件是否消失"为主，返回值只作辅助。**
2. **旧模块会占着 APP_ID 不放**：新模块 register 之后，屏幕上仍然是**旧模块**
   的页面（主页只有 5 行，没有新加的缓存清理行），看起来像"新代码没生效"。
   ⇒ 要验界面必须整机重启（`restart()`），不能只 rmmod。

**清理作业必须是增量的（一拍一个 VFS 动作）**：第一版把整棵目录树的
统计+删除放在一拍里做完，结果是**应用退出**（回到表盘），而目录里只少了
第一个文件 —— UI 线程被长时间 VFS 占死。改成增量作业后（开目录/读条目/
删文件各占一拍，路径前缀用栈记着）一次跑完 13 个文件、0 失败、应用存活。

**页面形状**（照 10P 的 `cacheclean.rs`）：四个根目录
（`/data/cache`、`/data/quickapp/cache`、`/data/log`、`/data/offlinelog`，
红线同样不碰 `/data/fitness/cache`），每个根一行显示"N 个文件 / 体积"，
第一行是"清理全部文件"，**两下才真删**（第一下把副标签改成"再点一次确认清理"）。
目录名去掉 `/data/` 前缀、两条标签宽度放到 300，否则"quickapp/cache"会被截断。

**这页带来的通用结论**：
- **长文件操作不许一次性做完**。固件里的 UI 定时器回调不是"想跑多久跑多久"，
  一拍里连删十几个文件就足以让应用被系统收掉。清理类操作一律拆成增量作业。
- **执行验证要造可分辨的读数**：文件删没删是"是/否"，比返回值更硬。
- **进页扫描**（只读遍历 + fstat 取大小）在 tick 之外的开销可以接受，
  13 个文件一次扫完没问题；贵的是删除。

### 83) 自动亮度开关：状态块指针是运行期重定位的字面量

亮度状态块在 PSRAM（guest 里读到 0x3C4965B8），但**静态拿不到它的地址**：
固件里是 `ldr r3,[pc,#0xc]` 取一个运行期被重定位过的字面量，文件里那个位置
存的是 0x65b8 这种小值。

**解法**：读**同一个字面量**。flash 里的地址是固定的（0x0CA65CBC），
运行期它被重定位成真指针（guest 里读回 0x3C4965B8）。
⇒ 模块里 `read_volatile(0x0CA65CBC)` 就是状态块指针，
`+0x04` 自动开关、`+0x08` 当前有效值、`+0x0C` 手动值都能直接读。

**执行验证**：进亮度页时自动那行显示"开"（guest 开机默认自动亮度是开的）；
点一下 → 状态块 `+0x04` 读回 0（关），页面重排。再点 50% 档 →
手动值被写成 128（固件随后又微调成 132，页面显示的是 getter 当时读到的 128）。

**通用结论**：**固件把全局块指针藏在重定位字面量里时，别去猜地址**——
固件自己怎么取的，就照着取那个字面量。写模块时直接读那个位置即可，
比"找一条会把它写出来的路径"省好几轮。

**这一页最终形状**：当前亮度（读回值/255）+ 25/50/75/100% 四档 + 自动亮度开关。
自动开着时点档位会先关掉自动（否则手动值不生效），再写手动值。

### 89) 震动页落地；顺带定案两条口径（运行地址加法 / 两个全局）

**先说教训**：§86/§87 里两次"一调就崩"的根因是**我把运行地址算错了**——
`file + 0x0C0C0000` 手算时少进了一位（`0x9B37A8` 写成 `0x0CA637A8`，正确是 `0x0CA737A8`；
`0x9B8988` 写成 `0x0C9B8988`，正确是 `0x0CA78988`）。
调错地址 = 跳进指令中间 = HardFault，表现出来就是 guest 503。
**规矩：地址一律用脚本现算（`python -c "print(hex(f + 0x0C0C0000))"`），不许心算。**

**震动两支（已执行验证）**：

| 用途 | file | 运行地址 | 判据 |
|---|---|---|---|
| `miwear_vibrator_run(pattern12)` | 0x9B37A8 | `0x0CA7_37A8` | 返回**震动 id**（成功时 ≥1，错误是负数 -2..-5）；实测返回 5、guest 存活 |
| `miwear_vibrator_set_mode(mode)` | 0x9B3910 | `0x0CA7_3910` | 写 `persist.vibration.mode`，成功后更新**强度全局** |

**两个不同的全局，别混**（这是本轮最容易搞错的地方）：

| 名字 | 指针字面量 | guest 里的值 | 谁在用 |
|---|---|---|---|
| 驱动用的"震动类型" | `0x0C92_B6D4` → PSRAM 字节 | 5 | `run()` 的 `pattern[0]` 必须等于它，否则驱动拒绝 |
| 用户设置里的"震动强度" | `0x0CA7_3950` → PSRAM 字节 | 1（标准）/ 2（增强） | `set_mode()` 写它 |

**页面形状**：`震动一次`（点一下按当前类型震一次）+ `强度`（只读显示 标准/增强）。
**没做**："标准/增强"两个可点行——`set_mode(2)` 时设置存储那一步失败（全局没变），
不能拿"点了没反应"的按钮充数，所以只留只读显示。
